# Задача для web-окружения: поиск, каталог кофе и модерация

Репозиторий: `CoffeePeek/coffeepeek-cross-web` — https://github.com/CoffeePeek/coffeepeek-cross-web.
Две независимые программы: `coffee-peek/` — пользовательская React 19/TypeScript/Vite программа; `coffee-peek-admin/` — административная программа на том же стеке.

Инструкция для web-агента: реализуй описанные ниже пользовательские и административные сценарии в отдельной ветке web-репозитория, проверь обе программы и подготовь PR. Сначала прочитай корневой `AGENTS.md`, `coffee-peek/CLAUDE.md` и `coffee-peek/DESIGN-SYSTEM.md`. Backend API реализованы в ветке PR #334; не меняй backend из web-задачи.

Источник API: контракт **`1.0.0`** в `docs/contracts/discovery-coffee.openapi.yaml` из актуальной ветки [backend PR #334](https://github.com/CoffeePeek/coffeepeek-backend/pull/334), репозиторий `CoffeePeek/coffeepeek-backend`. Статус контракта — `implemented-in-branch`; указанные API реализованы в этой ветке. Используй именно эту версию для генерации/проверки типов и сверяй DTO/коды ошибок с тем же backend commit. Базовый импорт и существующая административная модерация также описаны в `docs/coffee-catalog-api.md`. Ниже приведены ключевые правила и примеры; примеры используют вымышленные объекты.

Отдельно проверь развёрнутую версию backend по commit деплоя и HTTP smoke целевых маршрутов: наличие реализации в PR не означает, что production/staging уже обновлены. Зафиксируй base URL и backend commit, на котором проверяешь интеграцию; сверяй реальные ответы с контрактом `1.0.0`. Если нужная ветка ещё не развёрнута, разработку можно вести с соответствующим контракту mock, а проверку живого API выполнить после деплоя и явно отметить её статус в web PR.

## Результат для пользователя

1. Общий поиск кофеен и обжарщиков с одной строкой поиска и двумя секциями результатов. Общие фильтры — только способ приготовления и бюджет. У секций собственные страницы и количество результатов.
2. Отдельный поиск кофеен с существующими фильтрами. Сохранить карту, посещения, избранное, город, расписание, оборудование и фильтры кофеен.
3. Отдельный поиск обжарщиков с небольшим набором тегов услуг и отдельной группой требований к их ассортименту.
4. Отдельная вкладка «Кофе» с полноценным каталогом, фильтрами, сортировкой и карточкой вариантов покупки.
5. В admin — справочники тегов обжарщиков/характеристик кофе, назначения тегов, модерация кофе, защита ручных изменений от импорта и журнал импорта.

В текущем web-коде список кофеен находится в `coffee-peek/src/pages/CoffeeShopListPage.tsx` и компоненте `CoffeeShopList`; карточка обжарщика — `RoasterDetailPage.tsx`; маршруты — `src/routes/AppRoutes.tsx`. Не заменяй фильтры кофеен общими фильтрами. Добавь новый общий экран и самостоятельные страницы каталога обжарщиков/кофе, сохрани рабочие ссылки существующих страниц. Предлагаемые новые UI-маршруты: `/search`, `/roasters`, `/coffees`, `/coffees/:slug`. Используй slug и канонические публичные адреса; GUID нужны для admin-операций.

## API для пользовательской программы

Все HTTP-вызовы проходят через имеющийся `src/api/core/httpClient.ts`, серверные состояния — через React Query. POST search/facets являются чтением. Стандартная оболочка: `{ "isSuccess": true, "message": "...", "data": ... }`; существующий HTTP-клиент уже распаковывает/нормализует ответы — не распаковывай `data` дважды. Передавай `AbortSignal` из query function через HTTP-клиент.

| Метод и endpoint | Назначение |
| --- | --- |
| `POST /api/v1/discovery/search` | Общий поиск кофеен и обжарщиков |
| `POST /api/v1/coffee-shops/search` | Поиск кофеен и их собственные фильтры |
| `POST /api/v1/roasters/search` | Поиск обжарщиков, услуги и требования к кофе |
| `POST /api/v1/coffees/search` | Каталог кофе с фильтрами и сортировкой |
| `POST /api/v1/coffees/facets` | Доступные значения фильтров кофе и счётчики |
| `POST /api/v1/roasters/facets` | Значения фильтров обжарщиков и счётчики |
| `GET /api/v1/catalogs/roaster-tags` | Активные теги услуг обжарщиков |
| `GET /api/v1/catalogs/coffee-filter-values` | Активные нормализованные характеристики кофе |
| `GET /api/v1/coffees/{slug}` | Полная публичная карточка кофе |
| `GET /api/Catalogs/coffee-origin-countries` | Страны происхождения с ISO-кодами |
| `GET /api/v1/favorites` | Избранные кофейни и обжарщики текущего пользователя; JWT обязателен |
| `PUT /api/v1/favorites/{kind}/{slug}` | Добавить в избранное, без тела; идемпотентный ответ 204 |
| `DELETE /api/v1/favorites/{kind}/{slug}` | Удалить из избранного; идемпотентный ответ 204 |

Существующие GET `/api/CoffeeShops`, `/api/roasters`, `/api/coffees` и GET карточек продолжают существовать. Их старые DTO нельзя считать DTO новых v1-маршрутов. Профиль обжарщика загружается через существующий GET `/api/roasters/{slug}`; для его ассортимента использовать coffees/search с `filters.roasters: [slug]`.

### Общий поиск

```json
{
  "q": "roast",
  "filters": {
    "brew": ["filter"],
    "budget": {
      "currency": "BYN",
      "maxDrinkPrice": 12,
      "drinkVolumeMl": 250,
      "maxCoffeePrice": 50,
      "coffeeWeightGrams": 250
    }
  },
  "sections": ["coffee_shops", "roasters"],
  "sort": "relevance",
  "coffeeShops": { "page": 1, "pageSize": 10 },
  "roasters": { "page": 1, "pageSize": 10 }
}
```

Ответ `data` содержит `q`, `coffeeShops` и `roasters`. Каждая выбранная секция — `{ items, totalItems, totalPages, currentPage, pageSize }`; невыбранная секция — `null`, пустая выбранная — `items: []`, `totalItems: 0`, `totalPages: 0`. Общего total/общей страницы нет. Следующая страница обжарщиков не меняет страницу кофеен; изменение строки/общих фильтров сбрасывает обе страницы на 1. «Показать все» открывает соответствующую отдельную страницу с переносом применимых критериев.

Общие `brew` — `espresso` и `filter`. В кофейне brew+цена должны совпасть у одной доступной позиции меню; у обжарщика — у одного опубликованного кофе и одного доступного предложения. UI отображает `matchingMenuItems` в карточке кофейни и `matchingCoffee`/`matchingCoffeeProducts` у обжарщика как объяснение совпадения.

Сделай явно подписанные поля «Цена напитка» и «Цена пачки кофе», отдельные уточнения объёма/веса. Это разные бюджеты; их нельзя объединять в один ползунок или ранжировать как одну цену. Для цены пачки нужен `coffeeWeightGrams`, для бюджета нужна валюта. Диапазоны `minDrinkPrice/maxDrinkPrice` и `minCoffeePrice/maxCoffeePrice` независимы, минимум не выше максимума. В общий endpoint не передаются город, посещения, услуги обжарщика, кислотность или теги кофе. Без строки сортировка `name_asc`, с непустой строкой — `relevance`.

### Поиск кофеен

Пример `POST /api/v1/coffee-shops/search`:

```json
{
  "q": "",
  "filters": {
    "city": "minsk",
    "isOpen": true,
    "tags": ["specialty"],
    "origin": { "latitude": 53.9, "longitude": 27.56 },
    "radiusKm": 5
  },
  "sort": "distance_asc",
  "page": 1,
  "pageSize": 20
}
```

Дополнительные поля — `roasters`, `minRating`, `isNew`, `equipments`, `beans`, `brewMethods`, `priceRange`, `type`, `visitedOnly`, `favoritesOnly`, `menu`. Точные enum/формат `menu` бери из схем `ShopFilters`/`MenuFilters`. `tags` используют shop-tag slug, а не roaster-tag slug. Сортировки: `relevance`, `name_asc`, `distance_asc`, `rating_desc`; расстояние требует координаты. Геолокацию запрашивать только при выборе поиска рядом; отказ пользователя не ломает обычный поиск. Персональные фильтры требуют JWT. Сохрани знакомый UX избранного и карты; сохранение избранного подключи к новым `/api/v1/favorites` маршрутам, описанным ниже.

### Обжарщики: услуги отдельно от ассортимента

Первоначальные ручные теги услуг: `online-order` — онлайн-заказ, `pickup` — самовывоз, `subscription` — подписка, `wholesale` — опт, `training` — обучение. Загружай их из справочника, не зашивай полный список в JSX. Используй компактную группу «Услуги». Обжарка, кислотность и декаф идут в группе «Кофе в ассортименте», а не в постоянных тегах обжарщика.

```json
{
  "q": "",
  "filters": {
    "tags": ["wholesale"],
    "excludeTags": ["subscription"],
    "coffee": {
      "brew": ["filter"],
      "roast": ["light"],
      "acidity": ["low", "balanced"],
      "caffeine": ["decaf"],
      "weightGrams": 250,
      "currency": "BYN",
      "maxPrice": 50,
      "availableOnly": true
    }
  },
  "sort": "available_coffees_desc",
  "page": 1,
  "pageSize": 20
}
```

`tags` — AND; `excludeTags` исключает любого с назначенным тегом; наборы не пересекаются. Отсутствие тега не подтверждает отсутствие услуги: отрицательный вариант подписывать «Без тега „Подписка“», а не «Подписок нет». Вложенный `coffee.roasters` запрещён. Обжарщик подходит, только когда ОДИН его опубликованный кофе и подходящий вариант удовлетворяют всем критериям; нельзя собирать совпадение из декафа одного товара и светлой обжарки другого.

Сортировки: `relevance`, `name_asc`, `available_coffees_desc`. При критериях ассортимента последняя сортировка использует `matchingCoffeeProducts`, иначе `availableCoffeeProducts`. Показывай теги услуг, число доступных товаров, время проверки и подходящий кофе. В профиле обжарщика добавь раздел ассортимента с переходом в каталог и установленным фильтром по slug обжарщика.

### Каталог кофе

```json
{
  "q": "",
  "filters": {
    "roasters": ["sample-roaster"],
    "countries": ["ET", "CO"],
    "brew": ["filter"],
    "caffeine": ["decaf"],
    "roast": ["light"],
    "acidity": ["low", "balanced"],
    "processing": ["natural"],
    "taste": ["berry", "chocolate"],
    "weightGrams": 250,
    "currency": "BYN",
    "maxPrice": 50,
    "availabilityScope": "online",
    "availableOnly": true
  },
  "sort": "price_asc",
  "page": 1,
  "pageSize": 20
}
```

Дополнительно `productKind: roasted_beans|green_beans`, `productForm: whole_beans|ground_only`, `fermentation`, `composition`, `minPrice`. Отсутствующая группа/пустой массив не ограничивают выборку. AND между группами, OR внутри массива. Вес, валюта, цена, brew, область и наличие должны совпасть у одного предложения одного кофе. `availableOnly` по умолчанию true.

Нормализованные группы (значения приходят с сервера):

| Группа | Начальные значения |
| --- | --- |
| `brew` | `filter`, `espresso`, `omni` |
| `caffeine` | `regular`, `decaf`, `lowcaf` |
| `roast` | `light`, `medium`, `dark` |
| `acidity` | `low`, `balanced`, `bright` |
| `processing` | `washed`, `natural`, `honey`, `wet-hulled` |
| `fermentation` | `anaerobic`, `semi-anaerobic`, `experimental` |
| `taste` | `chocolate`, `nut`, `caramel`, `berry`, `citrus`, `tropical`, `floral`, `spicy` |
| `composition` | `single-origin`, `blend` |

Покажи основные фильтры сразу: назначение, кофеин, обжарка, кислотность, валюта/вес/цена, обжарщик. Страны, обработку, ферментацию, вкус, состав и форму помести в раскрываемый блок дополнительных фильтров. Сохранить все фильтры доступными, не превращать 29 начальных характеристик в 29 независимых кнопок верхней панели. «Неяркий» соответствует `low + balanced`; неизвестные данные не подходят. `omni` подходит выбранному filter/espresso по серверным правилам.

Сортировки: `relevance`, `name_asc`, `price_asc`, `price_desc`, `newest`. Цена требует одновременно `currency` и `weightGrams`; до выбора этих полей отключить обе ценовые сортировки и показать пояснение. Выбранный ценовой ключ — минимальная цена среди ВСЕХ подходящих предложений указанной фасовки; UI использует `sortPrice` сервера. Не сортируй только загруженную страницу. `newest` относится к созданию товара, а не ежедневному обновлению.

Карточка: `address`, `name`, `roaster`, `classification`, `countries`, `coverPhoto`, `matchingOffers`, `sortPrice`, `createdAtUtc`, `catalogCheckedAtUtc`, вид/форма продукта. В списке показывать исключительно `matchingOffers`, не более дешёвую неподходящую фасовку. Без валютного фильтра отображать суммы разных валют отдельно. Детальная карточка содержит `description`, `tasteDescriptors`, `photos`, ВСЕ `offers`, включая Unknown/OutOfStock. Фото показывать через серверные Media/imgproxy URL; при отсутствии — имеющуюся заглушку.

У предложения показать вес (`null` → «Вес не указан»), цену+валюту, помол/назначение, продавца, `online|in_store`, `InStock|OutOfStock|Unknown` и `checkedAtUtc`. Unknown → «Наличие не подтверждено», а не «Нет в наличии». InStock — результат проверки источника, не гарантия остатков. `checkedAtUtc` показывать в локальном времени пользователя. Покупка — внешняя ссылка `sourceUrl`; проверь допустимую схему http/https, `rel="noopener noreferrer"` при новой вкладке. Корзины и собственного checkout в этом контракте нет.

### Фасеты, адресная строка и состояние

В facets отправляется `{ q, filters }` без sort/page. Coffee facets возвращают `{ totalItems, groups, priceRange }`; roaster facets — `{ totalItems, groups }`. Группа содержит `code`, `name`, `selection: single|or|and`, `options: [{ code, name, count, selected }]`. Значения и счётчики серверные; не пересчитывай их по одной странице. Coffee count игнорирует текущий выбор своей OR-группы, сохраняет остальные критерии и не является суммой/приростом. Счётчики обжарщиков считают обжарщиков, а не кофе. Нулевые опции остаются видимыми, выбранные нулевые можно снять. `weightGrams.options.code` — строка, но в filters передаётся целое число. `priceRange` может быть null без валюты/веса или подходящих цен.

Фильтры, поисковую строку, сортировку и страницы сериализовать в URL; прямое открытие, reload, back/forward восстанавливают состояние. Раздельное состояние экранов/типов. Search debounce примерно 300 ms, старый запрос отменяется; поздний ответ не заменяет более новый. Смена любого применённого фильтра/сортировки сбрасывает страницу на 1. В мобильной панели разделить черновик выбора и «Применить», дать «Сбросить», индикатор количества активных фильтров и удаляемые chips. Не отправлять ещё не применённый черновик в основной поиск.

Query keys включают весь нормализованный запрос и пользователя/признак гостя там, где присутствуют личные поля. При logout/user switch отменить запросы и очистить персональные результаты; не разделять избранное между пользователями. Публичный поиск доступен гостям, но ответ с `isFavorite` для авторизованного пользователя тоже персональный, даже без `favoritesOnly`: не сохраняй его под общим гостевым ключом. При выборе персонального фильтра гостем показать существующий вход и сохранять намерение применить фильтр после входа.

Состояния: первоначальная загрузка — skeleton; обновление — сохранить прежние результаты с индикатором; пустая выдача — ясное сообщение и сброс фильтров; ошибка — сообщение и повтор; 400 `INVALID_FILTER` — ошибки у соответствующих полей; 401 — имеющийся auth flow; 404 карточки — «Кофе не найден»; 503/сетевая ошибка — временная недоступность с повтором. Не подавлять 400 и не подменять новый API старым API с клиентской фильтрацией. Если справочник изменился и сохранённый код деактивирован, предложить удалить этот фильтр, не менять его молча.

### Сохранение избранного

Все три маршрута избранного требуют JWT. `kind` принимает только `coffee_shop` или `roaster`, `slug` — публичный slug объекта. Backend определяет пользователя по JWT; не передавай `userId` в path, query или body. Для публичных карточек гостя `isFavorite: null` означает отсутствие персонального состояния, у авторизованного пользователя `true|false` приходит из БД. Локальное хранилище не должно подменять это состояние для вошедшего пользователя.

Пример `GET /api/v1/favorites`:

```json
{
  "isSuccess": true,
  "message": "Operation successful",
  "data": [
    {
      "kind": "roaster",
      "address": {
        "slug": "sample-roaster",
        "canonicalPath": "/roasters/sample-roaster",
        "revision": 1,
        "isAlias": false
      },
      "createdAtUtc": "2026-10-06T09:00:00Z"
    }
  ]
}
```

Добавление: `PUT /api/v1/favorites/roaster/sample-roaster` без тела. Удаление: `DELETE /api/v1/favorites/roaster/sample-roaster`. Обе операции возвращают 204 без JSON, повторные операции идемпотентны. Для кофейни используется `/api/v1/favorites/coffee_shop/{slug}`. Ответ GET — массив кратких адресов, не полные карточки; для экрана избранного с карточками используй соответствующие search endpoints с `favoritesOnly: true` и серверной пагинацией. Адрес из ответа использовать как канонический, не пытаться восстановить GUID по slug.

При нажатии сердца сделай optimistic update и сохрани прежнее значение для rollback. Пока мутация одного объекта выполняется, блокируй повторное нажатие либо сериализуй действия по `{ kind, slug }`, чтобы запоздавший PUT не отменил последующий DELETE. При сетевой/серверной ошибке откати состояние и покажи повтор. При 401 после стандартного refresh откати optimistic update и используй имеющийся вход; локально отмеченный результат не считается сохранённым. У гостя нажатие ведёт к auth flow, а не отправляет запрос без JWT. Отложенное намерение после входа связывается с текущим пользователем.

После успеха инвалидируй список избранного и соответствующие shop/roaster поиски, фасеты и карточки; сервер остаётся источником истины для `isFavorite`, total и `favoritesOnly`. Смена фильтра «Избранное» сбрасывает page=1. Удаление элемента из текущей выдачи `favoritesOnly` немедленно убирает его, сбрасывает страницу на 1 и перечитывает выдачу/счётчики, чтобы не оставлять пустую страницу с устаревшим total. Отложенный ответ или rollback от предыдущего аккаунта не должен менять кеш следующего аккаунта: перед применением результата проверь актуальный auth scope, при logout/user switch отмени запросы и мутации, очисти персональный кеш.

Добавь отдельные пункты «Кофе», «Импорт кофе», «Теги обжарщиков», «Характеристики кофе». Они не должны смешиваться с существующей очередью импорта кофеен. ### Модерация кофе

| Метод и endpoint | Действие |
| --- | --- |
| `GET /api/admin/coffees?status=Draft&page=1&pageSize=20` | Список черновиков; статусы Draft/Published/Archived |
| `GET /api/admin/coffees/{id}` | Полная карточка, предупреждения, version |
| `POST /api/admin/coffees` | `{ roasterId, content, countryCodes }`, ручной черновик |
| `PATCH /api/admin/coffees/{id}` | `{ content, countryCodes, protectedFields, status, version }` |
| `DELETE /api/admin/coffees/{id}` | Архивирование без физического удаления, ответ 204 |
| `GET /api/admin/coffees/{id}/classification` | Нормализованная классификация, варианты, защита, version |
| `PATCH /api/admin/coffees/{id}/classification` | Полная замена классификации и её защиты с version |
| `PATCH /api/admin/coffees/{id}/variants/{variantId}/classification` | `{ brewPurpose, protectFromImport, version }` |
| `PATCH /api/admin/coffees/public-addresses/{id}` | Изменение публичного slug по существующему контракту публичных адресов, только Admin |
| `GET /api/admin/coffee-import/runs?limit=30` | Журнал применения/ошибок, максимум limit=100 |

На списке дать фильтр статуса, пагинацию, переход в редактор. Редактор показывает описание, страны, характеристики, фото, все варианты покупки, предупреждения `reviewWarnings` и версию. Публичное имя/описание/характеристики и страны можно исправлять. Цены и наличие остаются данными источника; не создавать UI редактирования цен, запуска импорта, bulk publish, слияния дублей или rollback: соответствующих API нет.

Сценарий проверки: открыть Draft → проверить предупреждения/происхождение/фото → исправить содержание/классификацию → включить нужную защиту от импорта → опубликовать через PATCH `status: "Published"`. Архивирование подтверждается диалогом, сохраняет источники/фото. Для возвращения использовать PATCH статуса с актуальной версией. Ручной опубликованный кофе без предложений может отсутствовать в выдаче `availableOnly: true` — объяснить это в редакторе, не рисовать выдуманное предложение.

`content` базового DTO: `name`, `description`, `productKind`, `productForm`, `compositionKind`, `processing`, `roastLevel`, `acidity`, `body`, `qGraderScoreRaw`, `tasteDescriptors`, `brewRecommendations`, `grindOptions`, `features`. Для базовой защиты используются PascalCase: `Name`, `Description`, `ProductKind`, `ProductForm`, `CompositionKind`, `Processing`, `RoastLevel`, `Acidity`, `Body`, `QGraderScoreRaw`, `TasteDescriptors`, `BrewRecommendations`, `GrindOptions`, `Features`, `Countries`, `Photos`. Сохраняй полную форму из серверного DTO, не обнуляй поля, которые пока не имеют собственных controls.

Нормализованная классификация редактируется отдельно:

```json
{
  "classification": {
    "defaultBrewPurposes": ["filter"],
    "caffeine": "decaf",
    "roastLevel": "light",
    "acidity": "balanced",
    "processing": ["washed"],
    "fermentation": [],
    "tasteGroups": ["chocolate", "nut"],
    "composition": "single-origin"
  },
  "protectedFields": ["caffeine", "roastLevel", "acidity"],
  "version": 7
}
```

Для classification защита использует camelCase и заменяет ТОЛЬКО защиту классификации; защита базового content/стран/фото сохраняется. Не переносить один список protectedFields в другой. У каждой характеристики сделай отдельный control «Сохранять при импорте». null/[] означают «Не подтверждено»; не выставлять `regular` по умолчанию и не выводить single-origin только из одной страны. У варианта собственный `brewPurpose` имеет приоритет; `null` означает наследовать `defaultBrewPurposes`. Изменение варианта тоже увеличивает версию продукта.

Сохранение требует последнюю `version`; после любой успешной мутации перечитать/обновить общую версию. Не отправлять параллельно content, classification и variant PATCH с одной старой версией. При 409 `VERSION_CONFLICT` сохранить локальный черновик, показать «Карточка изменилась», предложить загрузить текущие данные/сравнить и повторить после решения пользователя; автоматическое перезаписывание запрещено. При выходе с несохранёнными изменениями использовать принятый в app механизм предупреждения.

Импорт создаёт новый кофе как Draft. Повторный успешный импорт обновляет Published без повторного подтверждения, сохраняет защищённые поля и не возвращает Archived в публикацию. Неизвестное новое значение не должно отображаться как команда очистить старую классификацию. В журнале показать источник, snapshotId, `Applied|Failed`, время сбора/применения, товары/варианты/добавленные, `missingAvailabilityApplied`, ошибку. Журнал — чтение; таймер на сервере не управляется браузером. Ошибка одного источника не означает, что импорт всех источников провалился.

## Проверка и критерии приёмки

1. Общий поиск возвращает и отображает обе группы; пустая одна группа не скрывает другую. Пагинация независима, общий бюджет напитка/пачки разделён, общая форма не посылает scoped-фильтры.
2. Собственные фильтры кофеен, карта, посещения и знакомый UX избранного продолжают работать; PUT/DELETE сохраняют избранное в backend после reload и на другом устройстве. У гостя `isFavorite=null`, у вошедшего пользователя true/false из БД; личные фильтры/нажатие сердца ведут к входу. Повторные PUT/DELETE корректно обрабатывают 204 без JSON, ошибка/401 откатывают optimistic update; смена favoritesOnly и удаление из его выдачи сбрасывают page=1.
3. Обжарщики фильтруются по услугам и по одному подходящему кофе/варианту. Проверить пару товаров, где условия разделены: такой обжарщик не должен проходить AND-критерии.
4. Кофе фильтруется сервером до пагинации; список показывает только подходящие варианты. Товар с дешёвой пачкой другого веса не показывает её как результат ценового фильтра 250 г. Ценовая сортировка требует валюту+вес, BYN/RUB не смешиваются.
5. Публичные значения загружаются из справочников; добавленное админом активное значение появляется без изменения JSX. Unknown данные не превращаются в regular/нет в наличии; изображения без фото получают заглушку.
6. URL/reload/back/forward восстанавливают критерии; смена фильтра сбрасывает page. Быстрый ввод/смена вкладки не допускают замены актуальных результатов поздним ответом.
7. Фасеты корректно отображают count=0 и позволяют снять выбранное нулевое значение. UI не складывает пересекающиеся счётчики как total.
8. Теги создаются/редактируются/деактивируются/реактивируются; назначения используют GUID и полную замену списка. Удаление тега сохраняет историю, новый PUT не пытается назначить неактивный тег.
9. Draft публикуется, Published архивируется и может быть восстановлен. Проверить отсутствие административных действий у обычного пользователя; изменение slug доступно только Admin.
10. Ручная классификация и базовый content не стирают защиту друг друга. Изменение варианта обновляет общую версию; 409 сохраняет локальные изменения и требует явного разрешения конфликта.
11. В журнале различимы Applied/Failed и состояние отдельных источников; нет неработающих кнопок импорта/rollback/редактирования цен.
12. Загрузка, пустые данные, 400, 401, 404, 409, 503 и сетевые ошибки проверены. Privacy-тест: пользователь A добавляет избранное → logout → пользователь B входит; карточки, список, totals/facets и favoritesOnly B не содержат данных A. Проверить также медленный GET/PUT/DELETE A, завершившийся после входа B: его ответ или rollback не меняют кеш B. Гость не получает последний персональный isFavorite из общего query cache; backend-вызовы никогда не отправляют userId.
13. Мобильная ширина 375 px и desktop, светлая/тёмная темы, keyboard navigation, подписанные controls, фокус/закрытие мобильного фильтра, контраст и skeleton не ломают дизайн-систему.

В обеих программах выполнить `npm ci`, доступные тесты, `npm run build`, отдельную проверку TypeScript по командам AGENTS/package.json. Добавить meaningful тесты для сериализации/восстановления фильтров, обязательных currency+weight, matchingOffers, независимой пагинации и обработки version conflict. Не ограничиваться snapshot-тестами JSX. Выполнить browser smoke публичного поиска/кофе и admin tag/publication/conflict flows с реальным backend либо явно отмеченным mock, соответствующим OpenAPI. В PR указать какой backend commit использован, какие проверки были на живом API, какие на mock, приложить mobile/desktop скриншоты. Если endpoint ещё не развёрнут, не выдавать mock-проверку за реальную интеграцию.
