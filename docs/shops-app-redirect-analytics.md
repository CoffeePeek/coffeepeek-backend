# AppDistribution redirect analytics: политика записи и восстановления

`GET /download/android`, `/download/apk` и `/download/ios` сначала разрешают действующий URL. После успешного разрешения контроллер создаёт один `EventId` и перед возвратом `302` передаёт `RecordAppDownloadRedirectCommand` в Wolverine. Конфигурация ShopsService включает PostgreSQL persistence, durable local queues и durable outbox. Обработчик записывает `AppDownloadRedirectEvent` с этим `EventId`; повтор уже записанного события пропускается.

Если постановка в очередь выбросила исключение, контроллер пробует выполнить **тот же** command синхронно через Wolverine. Успех означает, что запись завершилась до выдачи redirect; счётчик `shops.app_redirect.analytics_fallbacks` фиксирует такой путь. Ошибка обоих способов не прерывает уже разрешённый redirect, но увеличивает `shops.app_redirect.analytics_unconfirmed` и пишет error с `EventId` и одним из ограниченных channel. `User-Agent`, `Referer` и country не пишутся в лог.

Состояние после двойной ошибки **неопределённо**: первая отправка могла сохраниться без подтверждения, либо событие вообще не было записано. Идентификатор позволяет проверить `AppDownloadRedirectEvents` и durable очереди при разборе инцидента. Автоматически восстановить полностью потерянный запрос из логов невозможно, потому что исходные пользовательские поля намеренно не логируются. Поэтому метрика называется `unconfirmed`, а не `dropped`. Успешный HTTP redirect не является подтверждением записи аналитики.

`AppDownloadRedirectDurabilityLiveTests` проверяет inline-путь, идемпотентность и обычную доставку через durable local queue на PostgreSQL через настоящий Wolverine pipeline. Controller tests проверяют отказ очереди и двойной отказ. Физический restart процесса ShopsService/PostgreSQL, восстановление локальной очереди и фактическое выполнение live-теста в CI остаются отдельными выпускными проверками. RabbitMQ в этом локальном маршруте аналитики не участвует.
