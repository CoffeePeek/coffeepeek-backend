# OCR-задание меню: версия входа и жизненный цикл

Статус: схема и модель введены в P15; опубликованные магазины переведены на новый consumer в P16.

## Граница задания

Для опубликованного магазина `MenuOcrJob.Id` — идентификатор одной оплачиваемой попытки OCR. Задание хранит `ShopMenuId`, `MenuRevision`, SHA-256 полного набора фотографий и JSON фотографий, переданных именно этому запросу. При прикреплении новых фото вход OCR может быть подмножеством меню; hash при этом всегда отражает весь текущий набор. Порядок фотографий на hash не влияет. `ShopMenu.ActiveOcrJobId` выбирает последнее запрошенное задание.

`ShopMenu.InputRevision` начинается с 0 для существующих строк и монотонно увеличивается при любой ручной правке меню, изменении времени ручного захвата или состава фото. Автоматический OCR и смена статуса парсинга её не увеличивают. Ручной SQL-upsert обновляет revision тем же DB-level транзакционным блоком, что и позиции. Старое задание применимо только когда одновременно совпадают `ShopMenuId`, revision, hash фото и `ActiveOcrJobId`. Поэтому ручная правка отвергает весь старый результат, включая новые напитки и фото, а не только конфликтующие позиции. Новый consumer блокирует строки задания и меню через `SELECT … FOR UPDATE` перед проверкой и применением; проверки только на загруженном объекте недостаточно.

## Состояния

`Pending → Running → ResultStored → Applied` — успешный путь. `Pending/Running/ResultStored → Failed` — ошибка OCR; ответ провайдера с ошибкой сначала сохраняется в `ResultStored`. `Pending/Running/ResultStored → Stale` — вход устарел. Терминальные `Applied`, `Stale`, `Failed` не переходят в другие состояния. Результат нельзя заменить или применять до состояния `ResultStored`.

Новый `ParseMenuOcrJobRequestedEventHandler` не обёрнут Wolverine EF-транзакцией. Он фиксирует `Running` короткой транзакцией, затем вызывает провайдера, затем фиксирует `ResultJson` и `ResultStored` другой короткой транзакцией. Применение сохранённого результата и переход в `Applied` происходят вместе в третьей транзакции. Повтор после сохранения результата читает `ResultJson`; провайдер повторно не вызывается. Если redelivery видит `Running`, он не вызывает провайдера: возможный предыдущий платный вызов считается неопределённым и требует операторского решения. Сбой после ответа OCR, но до durable commit результата оставляет окно неопределённости и может оставить job в `Running` без результата. Для автоматического безопасного восстановления этого окна нужен поддерживаемый провайдером idempotency key/lookup или иной внешний протокол; локальная БД не даёт exactly-once billing.

## Совместимость при развёртывании

Имя и namespace `ParseMenuRequestedEvent`, существующий позиционный конструктор и conventional queue прежнего consumer сохранены. Новые поля `JobId`, `MenuRevision`, `PhotoSetHash` — nullable init-only. Новые команды опубликованного магазина создают job и публикуют отдельное `ParseMenuOcrJobRequestedEvent` через прежний transactional outbox. Сообщение P15 с `JobId` в старом envelope пересылается новому worker без платного OCR в старом consumer. Старое published-сообщение без `JobId` помещается в quarantine без вызова провайдера и без изменения меню, в том числе когда у существующей строки `InputRevision = 0` после миграции. Для операторского replay нужен явный новый job; автоматический replay старого published-сообщения небезопасен. Старые сообщения Moderation/ImportCandidate продолжают прежний маршрут.

Moderation и ImportCandidate публикуют тот же старый контракт без `JobId`. Их черновики хранятся в другой БД и не имеют `ShopMenu.InputRevision`; для draft OCR явно сохранён прежний lifecycle. Старый consumer возвращает `MenuParsedEvent` и больше не пишет live menu из этих сообщений. Их собственная stale-защита черновика не заявлена гарантией Shops lifecycle. `MenuParsedEvent.JobId` остаётся optional и не заполняется legacy draft consumer. Публикация снимка уже существующего магазина отдельно требует observed `ExpectedInputRevision`; old/null snapshot quarantined по [compatibility](../shops-contract-compatibility.md).

## Ограничения модели

Одна запись меню приходится на одно определение напитка (`ShopMenuId`, `DrinkDefinitionId` уникальны). Дубликат напитка в ручном batch отвергается целиком; OCR выбирает одну цельную пару цены и объёма. Это подтверждённое продуктовое правило, поэтому lifecycle задания не меняет cardinality позиций.
