# Владение бизнесом: API клиента и администратора

Все маршруты доступны через Gateway с `Authorization: Bearer <access-token>`. Пользователь может иметь несколько бизнесов; у каждого бизнеса один текущий владелец. Глобальные роли `Owner`/`Roaster` не требуются: сервер проверяет привязку пользователя к конкретной записи. После одобрения или отзыва повторный вход не нужен.

Успешные ответы используют `Response<T>`: `isSuccess`, `message`, `data`. Ошибки возвращаются с соответствующим HTTP-статусом через существующие `ErrorResponse`/`Response<T>` контракты. Чтение заявок, аудита и кабинета не предназначено для общего кеширования.

## Заявка пользователя

`POST /api/owner/ownership-claims`:

```json
{
  "businessType": "CoffeeShop",
  "businessSlug": "example-coffee",
  "contact": "manager@example.com",
  "evidence": "Управляю кофейней и могу подтвердить доступ к официальной почте."
}
```

`businessType` обязателен: `CoffeeShop` или `Roaster`. `businessSlug` — публичный slug существующего бизнеса, а не UUID. Обязательные `contact` и `evidence` ограничены 320 и 4000 символами соответственно после trim в доменных правилах. HTTP-модель также ограничивает исходную длину. Ссылки в подтверждении проверяет администратор вручную; сервер их не скачивает.

Заявитель определяется из аутентификации. Поля `applicantUserId`, `actorUserId`, статус и текущий владелец не задаются через тело запроса. Подача возвращает `201 Created`, заявку в `data` и `Location` для чтения деталей. POST ограничен Gateway policy `moderation-submission`.

| Запрос | Результат |
| --- | --- |
| `GET /api/owner/ownership-claims` | Собственная история; необязательный `status`, `page=1`, `pageSize=20` |
| `GET /api/owner/ownership-claims/{id}` | Собственная заявка и решение; чужая заявка возвращает `404` |

Публично недоступный или неизвестный бизнес — `404`. Уже назначенный владелец или собственная ожидающая заявка на этот бизнес — `409`. Повторная подача после отказа создаёт новую заявку, сохраняя историю старой.

Заявка содержит:

- `id`, `businessType`, `businessId`, `businessNameSnapshot`, `businessSlugSnapshot`;
- `applicantUserId`, `contact`, `evidence`, `createdAtUtc`;
- `status`: `Pending`, `Approved`, `Rejected`;
- `reviewedByUserId`, `reviewedAtUtc`, `decisionReason`;
- `hasCurrentAccess`: есть ли у заявителя доступ к бизнесу сейчас;
- `currentOwnerUserId`: доступен только в административном представлении, в ответах заявителю — `null`.

После отзыва доступа статус прежней одобренной заявки остаётся `Approved`, а `hasCurrentAccess` становится `false`. Кабинет должен ориентироваться на текущий доступ и списки своих бизнесов.

## Проверка администратором

Все маршруты этого раздела требуют `Admin`. Роль `Moderator` сама по себе не позволяет принимать решения по владению или читать контакты заявителей.

| Запрос | Параметры или тело |
| --- | --- |
| `GET /api/admin/ownership-claims` | `status` (по умолчанию `Pending`), `businessType`, `businessId`, `page`, `pageSize` |
| `GET /api/admin/ownership-claims/{id}` | Детали заявки и текущий владелец |
| `POST /api/admin/ownership-claims/{id}/approve` | `{ "reason": "Подтверждено через официальную почту" }`; комментарий необязателен, можно отправить `{}` |
| `POST /api/admin/ownership-claims/{id}/reject` | `{ "reason": "Не удалось подтвердить полномочия" }`; причина обязательна |
| `GET /api/admin/ownership-changes` | `businessType`, `businessId`, `page`, `pageSize` |

Причина решения ограничена 2000 символами. Новые списки возвращают `data.items`, `totalCount`, `page`, `pageSize`; допустимый размер страницы — от 1 до 100. У собственных заявок без фильтра возвращаются все статусы, у административной очереди без фильтра — ожидающие.

Одобрение одновременно сохраняет решение, назначает владельца и записывает аудит. Если бизнес уже занят, конкурентный запрос изменил состояние или аккаунт заявителя не удалось подтвердить, операция не выдаёт доступ и возвращает `409`. Если бизнес удалён — `404`. Сбой проверки аккаунта не превращается в автоматический отказ по заявке.

Повтор того же решения возвращает сохранённый результат без повторной выдачи прав. Противоположное решение по закрытой заявке возвращает `409`. Повтор старого approval после отзыва не восстанавливает владение. Конкурирующие заявки разных людей не позволяют перезаписать владельца, назначенного первым успешным решением.

## Кабинет и редактирование

| Кофейни | Обжарщики |
| --- | --- |
| `GET /api/owner/coffee-shops` | `GET /api/owner/roasters` |
| `GET /api/owner/coffee-shops/{id}` | `GET /api/owner/roasters/{id}` |
| `PUT /api/owner/coffee-shops/{id}` | `PUT /api/owner/roasters/{id}` |

Списки содержат только текущие привязки пользователя. `{id}` здесь — UUID из собственного кабинета. На чужие или больше не принадлежащие пользователю объекты сервер возвращает `404`.

Список обжарщиков принимает `page=1`, `pageSize=20` (максимум 100) и возвращает `data.items`, `totalCount`, `page`, `pageSize`. Детали обжарщика возвращают `RoasterDetailsDto` с `profileRevision`; успешный PUT — краткий `RoasterDto` с новой `profileRevision`. Для полного обновления формы после сохранения перечитайте детали.

Для кофейни сохраняется существующий контракт профиля: имя, описание, телефон, email, сайт, Instagram, расположение, расписание и связи со справочниками. Существующий `If-Match` необязателен для совместимости, но клиент должен отправлять прочитанную `profileRevision` при сохранении.

Профиль обжарщика содержит имя, описание, город/адрес/координаты, сайт, Instagram и фотографии. На owner PUT обжарщика заголовок `If-Match` обязателен:

```http
PUT /api/owner/roasters/{id}
Authorization: Bearer <access-token>
If-Match: "7"
Content-Type: application/json
```

```json
{
  "name": "Example Roasters",
  "about": "Обжариваем кофе небольшими партиями",
  "cityId": null,
  "address": null,
  "latitude": null,
  "longitude": null,
  "instagramLink": "https://www.instagram.com/example",
  "siteLink": "https://example.com",
  "photos": null
}
```

PUT сохраняет профиль целиком: передавайте текущие значения полей, которые нужно сохранить. `photos: null` оставляет галерею без изменений, `photos: []` очищает её, массив задаёт полный состав и порядок. Отсутствующий `If-Match` — `428`, некорректный — `400`, устаревший — `409`; перечитайте профиль и согласуйте изменения перед повтором. У admin PATCH обжарщика `If-Match` остаётся необязательным для совместимости.

После сохранения изменения становятся публичными сразу. Владелец не получает права редактировать пользовательские отзывы, фотографии посещений, меню/цены или товары обжарщика через эту функцию.

### Фотографии

Для новых фотографий используются существующие Media endpoints `POST /api/Photos/shop` и `POST /api/Photos/roaster`: получить presigned URL, загрузить файл, передать metadata/key в операцию галереи. Сервер проверяет принадлежность новых загрузок текущему пользователю.

Для кофеен сохраняются:

- `POST /api/owner/coffee-shops/{id}/photos` с `photos`;
- `DELETE /api/owner/coffee-shops/{id}/photos` с `photoIds`;
- `PUT /api/owner/coffee-shops/{id}/photos/order` с полной перестановкой `photoIds`.

Обжарщик меняет галерею через профильный PUT. Сохранённые фотографии, в том числе загруженные прежним владельцем или администратором, сохраняют свои Media ID; смена владельца не требует повторной загрузки. Новые чужие ключи не принимаются.

## Назначение и отзыв доступа

`PATCH /api/admin/shops/{id}/owner` и `PATCH /api/admin/roasters/{id}/owner` требуют `Admin`:

```json
{
  "ownerUserId": null,
  "reason": "Представитель больше не управляет бизнесом"
}
```

`ownerUserId: null` снимает доступ; UUID назначает указанного пользователя. Для нового roaster endpoint причина отзыва обязательна. Старый shop endpoint сохраняет совместимость запросов без причины и фиксирует служебную причину в аудите; новый клиент всегда должен отправлять её. Выполнивший операцию администратор берётся из аутентификации.

Отзыв действует с коммита операции. Последующие чтения/правки прежнего владельца недоступны. Правка, начатая до отзыва, но сохраняемая после него, должна завершиться конфликтом/отказом в доступе. История в `/api/admin/ownership-changes` сохраняет бизнес, предыдущего и нового владельца, исполнителя, причину, время и связанную заявку, если она была.

Загрузка документов, сотрудники с отдельными ролями, автоматическая проверка бизнес-почты, уведомления о решениях и автоматическое снятие привязок при удалении аккаунта не входят в эту версию. Для удалённого аккаунта администратор может снять назначение вручную.

## Локальная сквозная проверка

`dev/ownership-smoke.py` использует только стандартную библиотеку Python и работает через запущенный локальный Gateway. Нужны применённые миграции, работающие Shops/Account и инфраструктура, включённые публичные адреса (`PublicAddresses:Enabled`) и два действующих токена в переменных окружения:

- `USER_TOKEN` — обычный пользователь без административной роли;
- `ADMIN_TOKEN` — администратор;
- `BASE_URL` — явно заданный loopback URL Gateway.

После установки токенов в окружении запустить из корня в PowerShell:

```powershell
$env:BASE_URL = 'http://127.0.0.1:8080'
python dev/ownership-smoke.py
```

Скрипт сначала проверяет разделение ролей, затем создаёт отдельного временного обжарщика и проходит подачу → одобрение → чтение кабинета → сохранение полного профиля с `If-Match` → публичное чтение → отзыв → отказ в чтении и записи → повтор старого approval без восстановления доступа. Во всех owner-запросах используется тот же токен. Изменяется только описание временного обжарщика; остальные поля сохраняются, `photos: null` оставляет галерею.

В блоке `finally` временный обжарщик удаляется. Заявка и аудит остаются в локальной БД, как предусмотрено моделью истории. При неуспешной очистке выводится только ID временной записи для ручного удаления. Токены и HTTP-тела ошибок не выводятся. Нелокальные адреса, redirects и HTTP-прокси окружения не используются.

Этот сценарий проверяет обжарщика и не меняет существующие кофейни. Проверки изоляции доступа и записи кофеен находятся в .NET HTTP/application/live-тестах. Проверка самого smoke-скрипта без сети:

```text
python dev/test_ownership_smoke.py
```


## Фото подтверждения — контракт 2026-10-29

Перед выпуском клиента применить Shops-миграцию
20261029083139_AddOwnershipEvidencePhotos и Media-миграцию
20261029083142_AddOwnershipEvidencePhotos и 20261029100047_AddOwnershipEvidenceBindings.

POST /api/Photos/ownership-evidence принимает multipart/form-data с полем file:
авторизованный пользователь, до 5 MiB. Response<T>.data содержит photoId,
storageKey и пустой uploadUrl; публичной ссылки нет. Media декодирует изображение,
проверяет максимум 8192 по стороне / 32 мегапикселя и сохраняет его в существующем
закрытом bucket с назначением OwnershipEvidence. До подачи фото помечено временным.

POST /api/owner/ownership-claims дополнен необязательным evidencePhotoIds:
до трёх различных UUID этой загрузки. Старые текстовые заявки совместимы.
Чужие, просроченные, отсутствующие, использованные другой заявкой или публичные
фото не принимаются. Привязка фото не выдаёт права на бизнес. После отказа сервер
разрешает повторную подачу с фото из последней отклонённой заявки того же
пользователя на тот же бизнес. Новая попытка получает новый ID; повтор этой
попытки после сбоя между коммитами Media и Shops сохраняет её ID и резервирование.
Media добавляет отдельную связь фото с новой заявкой, сохраняя прежнюю связь
и чтение вложений в истории. Источник повторного использования определяет Shops
по сохранённому решению; клиент не может указать произвольную прежнюю заявку.
Публичные DTO мобильного клиента не меняются.

Ответы заявок дополнены evidencePhotoIds. Бинарное чтение:
GET /api/owner/ownership-claims/{id}/photos/{photoId} — только заявитель;
GET /api/admin/ownership-claims/{id}/photos/{photoId} — только Admin.
Оба сверяют photoId с составом доступной заявки и возвращают private, no-store
и nosniff. Публичных GET и presigned download URLs нет.

Списки собственных кофеен/обжарщиков дополнены publicSlug: публичный мобильный
профиль использует slug, а owner PUT требует UUID. Клиент связывает их через
собственные списки. Публичная идентичность профиля не меняется.

Бизнес-режим — состояние клиентской навигации текущего аккаунта, не выдающее
серверные разрешения. Собственные списки перепроверяются перед включением и на
возврате приложения. Owner PUT с If-Match публикует профиль сразу.
