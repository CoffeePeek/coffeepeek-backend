# Каталог кофе: запуск и API

Реализовано в PR #334, дополнено 6 октября 2026 года. Каталог хранится в Shops; фотографии — в существующем Media/MinIO. Новые API поиска, справочников и классификации описаны в [OpenAPI 1.0.0](contracts/discovery-coffee.openapi.yaml). Изменения проверены локально и в PR CI; миграции в production и активация таймера на VPS ещё не выполнены.

## Запуск

1. Применить миграции Shops до `AddDiscoveryClassificationsAndFavorites` обычной командой из `AGENTS.md`. Предыдущая `AddCoffeeCatalogAndRoasterTags` создаёт девять таблиц и 30 стран; Республика Конго имеет код `CG`. Новая добавляет нормализованную классификацию, избранное и справочники. Существующий `CoffeeBean` не переносится. Дополнительная миграция Media не требуется: используется существующая таблица `Photos`.
2. Заполнить [roaster-mapping.example.json](../dev/coffee-import/roaster-mapping.example.json) реальными GUID существующих обжарщиков. Добавить раздел `CoffeeImportOptions` в конфигурацию Shops (`appsettings.Production.json` либо эквивалентную конфигурацию развёртывания). Сам файл примера автоматически не загружается. Нулевые GUID — заглушки и не принимаются импортом. Бренд сопоставляется точно; неизвестный бренд и отсутствующий обжарщик отклоняются. В магазине Сова нужны два отдельных обжарщика: KOF и Kanga.
3. В Shops и Media задать одинаковый случайный `CoffeeImportAuthOptions__Token` длиной не менее 32 символов. Пустой токен отключает служебные endpoints. Настроить существующие `MinIOOptions` и `MediaPublicUrlOptions`; бакет Shops должен быть доступен для записи из Media и чтения по публичному адресу. `MediaPublicUrlOptions__ImageProxyEndpoint` добавляет URL размеров через imgproxy.
4. Джобе передать тот же токен и внутренние адреса сервисов через [coffee-import.env.example](../dev/coffee-import/coffee-import.env.example). Эти переменные задаются процессу Python отдельно от процессов .NET. Служебные маршруты не проксируются через Gateway.
5. Выполнить настройку, проверку одного источника и активацию таймера по [инструкции развёртывания](coffee-import-deployment.md). Скрипт установки сохраняет Python-окружение вне checkout и оставляет таймер выключенным до успешной проверки. Плановый запуск — 03:00 UTC, пропущенный запуск выполняется после старта сервера.

Новые товары всегда `Draft`. Администратор проверяет страны и характеристики, затем устанавливает `Published`. Последующие успешные импорты обновляют опубликованный товар без повторной публикации; защищённые поля остаются ручными. Миграция добавляет пять тегов услуг обжарщика: онлайн-заказ, самовывоз, подписка, опт и обучение. Назначения остаются ручными, импорт их не меняет. Характеристики ассортимента (например, декаф или светлая обжарка) вычисляются по подходящему опубликованному кофе, а не записываются тегами услуг.

## Поиск v1

Новые POST-маршруты читают данные и используют стандартную оболочку `Response<T>`. Фильтрация и сортировка выполняются в БД до пагинации. Полные DTO, допустимые значения, ошибки и примеры находятся в OpenAPI.

| Метод и маршрут | Результат |
| --- | --- |
| `POST /api/v1/discovery/search` | Кофейни; общие фильтры заваривания и бюджет напитка |
| `POST /api/v1/coffee-shops/search` | Собственные фильтры кофеен, меню, расстояние, рейтинг, посещения и избранное |
| `POST /api/v1/coffees/search` | Нормализованные характеристики, страны, обжарщик, вес, валюта, цена и наличие; сортировки имени/релевантности/цены/новизны |
| `POST /api/v1/coffees/facets` | Доступные значения и счётчики с сохранением остальных критериев |
| `GET /api/v1/catalogs/roaster-tags` | Активные теги услуг |
| `GET /api/v1/catalogs/coffee-filter-values` | Активные значения восьми групп характеристик кофе |
| `GET /api/v1/coffees/{slug}` | Публичная карточка и все предложения покупки |
| `GET /api/v1/favorites` | Избранные кофейни/обжарщики/напитки текущего пользователя |
| `GET /api/v1/profiles/{authorSlug}/favorites` | Публичное избранное пользователя; [контракт профиля](api/profiles.md) |
| `PUT/DELETE /api/v1/favorites/{kind}/{slug}` | Идемпотентное добавление/удаление избранного, ответ 204 |

В общем поиске нельзя передавать специфичные фильтры кофеен. Обжарщики доступны полным списком `GET /api/roasters`. Кофе вынесен в самостоятельный каталог. При цене пачки и ценовой сортировке требуются валюта и вес. Цена, вес, наличие и назначение должны совпасть у одного предложения. В списке кофе возвращаются только `matchingOffers`, в карточке — все предложения. Между группами характеристик действует AND, внутри одной группы — OR; теги услуг обжарщика используют AND. Вручную оставленная неизвестной классификация не подтверждает значение фильтра; при импорте кофеин по умолчанию обычный. Отсутствие данных об услуге не подтверждает её отсутствие.

Восемь фиксированных групп: назначение, кофеин, обжарка, кислотность, обработка, ферментация, вкусовая группа и состав. Миграция добавляет 29 начальных значений; администратор может расширять значения внутри групп. Нормализация импорта сохраняет прежние данные при неизвестном значении. Кофеин при импорте по умолчанию `regular`: декаф/лоукаф распознаются по характеристикам, затем названию и описанию товара. Прочие признаки требуют явных характеристик; защищённые вручную поля сохраняются. Новое значение справочника само по себе не меняет правила парсера.

Страна происхождения, однозначно указанная в названии кофе без признака смеси, применяется автоматически; основание `name` остаётся в исходном снимке. Страна из названия смеси, несколько стран, неоднозначное «Конго» и отсутствующее основание требуют подтверждения. Неизвестный код страны не добавляется в справочник автоматически.

Публичный поиск и избранное профиля доступны гостю. Собственное избранное, его изменение и персональные фильтры требуют JWT, пользователь определяется сервером. Ответы поиска не кешируются; клиентский кеш должен учитывать пользователя, поскольку `isFavorite` персонален даже без фильтра избранного.

## Пользовательские маршруты через Gateway

Ответы используют стандартный `Response<T>` проекта; содержимое находится в `data`.

| Метод и маршрут | Результат |
| --- | --- |
| `GET /api/Catalogs/coffee-origin-countries` | `code`, `nameRu`, `nameEn`; код используется клиентом для флагов |
| `GET /api/Catalogs/roaster-tags` | Активные теги со стабильным slug |
| `GET /api/roasters` | Полный список без пагинации: адрес, название, фото, теги, счётчики кофеен и кофе |
| `GET /api/roasters/{slug}` | Существующий профиль с полями `tags`, `coffeeShopsCount`, `coffeeProductsCount`, `availableCoffeeProducts` |
| `GET /api/roasters/{slug}/coffees` | Опубликованные кофе этого обжарщика |
| `GET /api/coffees` | Общий опубликованный каталог |
| `GET /api/coffees/{slug}` | Карточка кофе и варианты покупки |

`GET /api/roasters` возвращает `data` как массив, без `items`, `page`, `pageSize` и `totalPages`. Необязательный фильтр: `?tags=wholesale&tags=training` (AND по активным тегам). Сортировка: число опубликованных позиций кофе по убыванию, затем число видимых кофеен по убыванию, затем название по алфавиту и ID. Размер каталога учитывает опубликованное кофе независимо от наличия; фасовки, Draft и Archived не увеличивают счётчик. Теги упорядочены по `sortOrder`, затем по названию; неактивные теги скрыты. Старый `GET /api/Catalogs/roasters`, поиск и фасеты обжарщиков удалены, секции обжарщиков в общем поиске больше нет. Дата обновления каталога не возвращается в списке и профиле обжарщика; даты предложений и кофе сохраняются.

```json
{
  "data": [
    {
      "address": { "slug": "roast", "canonicalPath": "/roasters/roast", "revision": 1, "isAlias": false },
      "name": "ROAST",
      "photoUrl": "https://media.example/roasters/roast.jpg",
      "coverPhoto": null,
      "tags": [{ "slug": "wholesale", "name": "Оптовые поставки", "description": null, "sortOrder": 0 }],
      "coffeeShopsCount": 7,
      "coffeeProductsCount": 20,
      "availableCoffeeProducts": 18
    }
  ],
  "isSuccess": true
}
```

В списках и профиле обжарщика `coffeeShopsCount` считает видимые кофейни, а `coffeeProductsCount` — разные опубликованные позиции кофе, независимо от фасовки и наличия. Draft/Archived исключены. `availableCoffeeProducts` сохраняет отдельный смысл: опубликованные позиции с вариантом InStock. Счётчики вычисляются из БД при чтении, без отдельной таблицы и без запроса на каждого обжарщика. В сокращённых ссылках на обжарщика внутри ответов кофеен счётчики могут быть `null`, если статистика не запрашивалась.

Фильтры каталога: `roasterSlug`, `search`, повторяемый `countries=ET&countries=CO`, `productKind=roasted_beans|green_beans`, `processing`, `brew`, `weightGrams`, `currency=BYN|RUB`, `minPrice`, `maxPrice`, `availableOnly` (по умолчанию `true`), `page`, `pageSize` (1–100). Несколько стран — OR, несколько тегов обжарщика — AND. Фильтры веса, цены, валюты и наличия проверяются у одного варианта. Для диапазона цен обязательно указать валюту.

Сортировка кофе по имени сначала выдаёт названия, начинающиеся с букв или цифр, затем со спецсимволов (включая `_`); внутри групп сохраняется алфавитный порядок. Это правило применяется до пагинации в общем каталоге, каталоге обжарщика, административном списке и `POST /api/v1/coffees/search`. В поиске приоритет цены, новизны и релевантности сохраняется; правило имени используется при равенстве основного критерия. Последний критерий — ID в обычном каталоге и slug в поиске. Классы Unicode в PostgreSQL определяются локалью БД.

Карточка содержит `address`, `roaster`, `content`, `countries`, `photos`, `variants`, `updatedAtUtc`. `photos[]` имеет `fullUrl`, `urls` (размеры существующего `PhotoUrlsDto`), `isPrimary`, `sortIndex`. Это ссылки на сохранённые файлы Media, доступные независимо от исходного сайта. `photos=[]` означает отсутствие фотографии; клиент показывает заглушку.

Вариант содержит `weightGrams` (может быть `null`), `price`, `currency`, `grind`, `roastPurpose`, `availability`, `availabilityScope`, `sellerName`, `sourceUrl`, `checkedAtUtc`. Наличие: `InStock`, `OutOfStock`, `Unknown`; область: `online` или `in_store`. River даёт наличие в кофейне. Оформление заказа происходит по `sourceUrl` на сайте продавца. Изменения каталога читаются из БД со следующего запроса, ответы не кешируются.

## Административные маршруты

Требуются существующие роли Moderator/Admin. GUID используются в административных операциях.

| Метод и маршрут | Действие |
| --- | --- |
| `GET /api/admin/coffees?status=Draft` | Черновики, предупреждения, фотографии и версия карточки |
| `GET /api/admin/coffees/{id}` | Полная карточка для редактирования |
| `POST /api/admin/coffees` | Создание ручного черновика: `roasterId`, `content`, `countryCodes` |
| `PATCH /api/admin/coffees/{id}` | Полные `content`, `countryCodes`, `protectedFields`, `status`, последняя `version` |
| `DELETE /api/admin/coffees/{id}` | Архивирование без удаления источников и фото |
| `GET/POST /api/admin/roaster-tags` | Справочник / создание: `slug`, `name`, `description`, `sortOrder` |
| `PATCH /api/admin/roaster-tags/{id}` | `name`, `description`, `sortOrder`, `isActive` |
| `DELETE /api/admin/roaster-tags/{id}` | Деактивация; назначения сохраняются, публично скрыты |
| `GET /api/admin/roasters/{id}/tags` | Назначенные теги, включая неактивные |
| `PUT /api/admin/roasters/{id}/tags` | Замена назначений: `{ "tagIds": [...] }`; допускаются активные теги |
| `GET /api/admin/coffee-import/runs?limit=30` | Применённые/неуспешные снимки и ошибки |
| `GET/POST /api/admin/coffee-filter-values` | Справочник нормализованных характеристик / новое значение внутри фиксированной группы |
| `PATCH /api/admin/coffee-filter-values/{id}` | Название, описание, порядок, активность; код и группа постоянны |
| `DELETE /api/admin/coffee-filter-values/{id}` | Деактивация с сохранением исторических назначений |
| `GET/PATCH /api/admin/coffees/{id}/classification` | Классификация и отдельный список защищённых полей с последней версией продукта |
| `PATCH /api/admin/coffees/{id}/variants/{variantId}/classification` | Назначение заваривания варианта и защита от импорта; обновляет общую версию |

`protectedFields` использует имена: `Name`, `Description`, `ProductKind`, `ProductForm`, `CompositionKind`, `Processing`, `RoastLevel`, `Acidity`, `Body`, `QGraderScoreRaw`, `TasteDescriptors`, `BrewRecommendations`, `GrindOptions`, `Features`, `Countries`, `Photos`. Защита `Photos` сохраняет текущую галерею при следующем импорте. Цены и наличие остаются данными источника. Несвежая `version` при сохранении возвращает 409: клиент перечитывает карточку.

Нормализованная классификация имеет собственную защиту в camelCase (`caffeine`, `roastLevel`, `acidity` и другие имена из OpenAPI); она не заменяет защиту базового содержания. Сохранение классификации/варианта требует общую актуальную версию кофе. При конфликте возвращается `409 VERSION_CONFLICT`. Значения справочника деактивируются, публично скрываются и сохраняются в административной истории; код остаётся зарезервированным. Цены, остатки, запуск импорта, массовая публикация и откат снимков не редактируются через эти API.

Администратор с ролью Admin может менять slug через существующий `/api/admin/coffees/public-addresses/{id}` по контракту публичных адресов проекта; прежние ссылки разрешаются через aliases.

## Внутренний обмен

Требуется заголовок `X-Coffee-Import-Token`. Доступ — по внутренней сети напрямую к Media/Shops.

| Endpoint | Контракт |
| --- | --- |
| `POST /internal/coffee-photos` в Media | Multipart `file`, растровое фото до 8 MiB → `id`, `storageKey`, `fileName`, `contentType`, `sizeBytes` |
| `POST /internal/coffee-import/snapshots` в Shops | `{ "sourceKey": "roast.by", "snapshotId": "<sha256>", "snapshot": {...} }`, до 16 MiB |
| `POST /internal/coffee-import/failures` в Shops | `sourceKey`, `snapshotId`, `collectedAtUtc`, `stage=collect|photos|apply`, `error` |

Сначала фотографии сохраняются в MinIO, затем их подтверждённые метаданные добавляются к снимку в `storedPhotos`. Повторное содержимое использует ключ `coffees/<sha256>.<ext>`. Применение одного источника транзакционное; повтор идентичного снимка возвращает прежний результат. Новый устаревший снимок отклоняется. Старый уже применённый идентификатор остаётся идемпотентным. Изменённое содержимое под прежним идентификатором отклоняется.

Страны, извлечённые только из названия, требуют подтверждения и остаются предупреждениями. Неизвестные коды не пополняют справочник автоматически. Отсутствие поля/фото в очередном снимке не очищает прежнее значение. Для сайтов без независимого счётчика исчезнувшая карточка не снимается автоматически; явно недоступные карточки переводятся в `OutOfStock`, проверенное исчезновение — в `Unknown`.

Проверки включают импорт 15 сохранённых каталогов (447 карточек, 886 вариантов), повтор снимка, сохранение ручных полей/тегов/фото, публикацию/архивирование, деньги и фильтры. Media сохраняет исходные байты и не загружает повторный объект. HTTP-тесты проверяют маршруты, DTO, авторизацию и ошибки. Пять интеграционных тестов выполнены на настоящем PostgreSQL 17: миграции, массивы классификации, конфликт версии, совпадение одного предложения, SQL-фильтрация/сортировка, фасеты и фильтры кофеен. В CI добавлены Media, Python, проверка скриптов развёртывания и отдельный запуск PostgreSQL-тестов.

Финальный локальный Release-прогон: 1583 .NET теста прошли, 28 инфраструктурных тестов пропущены без конфигурации; пять PostgreSQL-тестов из них запущены отдельно и прошли. Python: 27 тестов прошли. OpenAPI 1.0.0: все локальные ссылки и 20 примеров валидны, сгенерированные DTO совпадают со схемой. NuGet-аудит не обнаружил уязвимых пакетов.

На изолированном PostgreSQL 17 и настоящем MinIO выполнен HTTP-цикл с синтетическим снимком: авторизация служебных endpoints, создание Draft, повтор снимка/фото без дублей, сохранение и чтение исходных байтов изображения, публикация и фильтрация/ценовая сортировка, карточка по slug, повторный импорт с сохранением Published и ручной защиты имени/фото. Это локальная проверка серверов с конфигурацией Production, без обращения к рабочим данным и сайтам источников.

Активация на VPS требует реального GUID-сопоставления обжарщиков и успешного smoke-теста из инструкции развёртывания. Ни локальные тесты, ни наличие контракта не означают, что production уже обновлён.
