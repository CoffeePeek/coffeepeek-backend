# ShopsService: таблицы решений для P02

Дата исследования: 8 октября 2026 года. **Утверждено пользователем:** ADR-01 — пустое расписание означает «неизвестно» во всех API; ADR-02 — расписание поступает в UTC и вычисляется в UTC; ADR-03 — позиция `Present` требует строго положительных цены и объёма, OCR-строка без любого из этих значений пропускается, дубль напитка в ручном пакете отклоняет весь пакет; ADR-04 — одна позиция меню на напиток; ADR-05 — любая ручная правка после запуска OCR делает его результат устаревшим и отклоняет его целиком; ADR-06 — удаление используемого города отклоняется как конфликт; ADR-07 — основное оборудование выбирается отдельно для каждой кофейни; ADR-08 — admin/owner сверяют одну ревизию всего профиля. Остальные изменения бизнес-поведения ниже — предложения. Неутверждённые варианты не следует выдавать за требования продукта.

Основание: [план P02–P03](shops-modularization-plan.md), [аудит](shops-architecture-audit.md), исходники по ссылкам ниже. `null`, пустое значение и неизвестное значение здесь различаются намеренно.

## ADR-01. Пустое расписание, закрытие и `IsOpen` — утверждено

**Сейчас.** `ShopScheduleEvaluator.IsOpenAtUtc` считает пустой набор расписаний открытым. Legacy search повторяет эту трактовку. Discovery исключает такие кофейни из фильтров `isOpen=true` и `isOpen=false`, а в карточке отдаёт `IsOpen=null`. Состояния `TemporarilyClosed` и `PermanentlyClosed` имеют иной смысл, чем административное `IsHidden`. Источники: [оценка часов](../CoffeePeek.Shops.Domain/Aggregates/CoffeeShopAggregate/ValueObjects/ShopScheduleEvaluator.cs), [legacy-запрос](../CoffeePeek.Shops.Persistance/Queries/CoffeeShopQueries.cs), [Discovery](../CoffeePeek.Shops.Persistance/Discovery/DiscoveryQueryStore.Shops.cs), [профиль](../CoffeePeek.Shops.Domain/Aggregates/CoffeeShopAggregate/CoffeeShop.cs).

**Утверждено пользователем.** Пустое расписание означает `Unknown` во **всех** API: карточка возвращает nullable `isOpen=null`; фильтры `true`/`false` исключают неизвестное. Для действующей кофейни явно закрытый день означает `false`, а не `Unknown`. Закрытый по статусу объект даёт `false` при наличии профиля, если этот объект вообще доступен в соответствующем административном API. Скрытый объект отсутствует из публичной выдачи независимо от часов.

| Пример при UTC 10:00 | Публичная карточка | `isOpen=true` | `isOpen=false` |
| --- | --- | --- | --- |
| Active, расписание `[]` | `null` | нет | нет |
| Active, сегодня 09:00–18:00 UTC | `true` | да | нет |
| Active, сегодня `IsClosed=true` | `false` | нет | да |
| TemporarilyClosed/PermanentlyClosed | нет в публичной выдаче; в admin — `false` | нет | нет |
| Active, `IsHidden=true` | нет | нет | нет |

**Совместимость.** Пользователь явно выбрал единую семантику также для legacy API; сохранять там старое `true` нельзя. Текущие legacy DTO содержат `bool IsOpen`, поэтому потребуются `bool?`, проверка сериализации и клиентов: JSON поле останется `isOpen`, но теперь может иметь `null`. Это изменение контракта должно быть учтено в P23/P34 и при необходимости версионировано на границе клиента. Решение о доступности закрытых/скрытых объектов в разных ролях остаётся предметом отдельной проверки существующих правил, не меняет значение пустого расписания.

## ADR-02. Временная зона расписания — утверждено

**Сейчас.** `IsOpenAtUtc` требует `DateTimeKind.Utc`, интервалы и дни недели трактуются в UTC, включая переход через полночь. Хранения IANA zone ID в профиле нет. Источник: [ShopScheduleEvaluator](../CoffeePeek.Shops.Domain/Aggregates/CoffeeShopAggregate/ValueObjects/ShopScheduleEvaluator.cs).

**Утверждено пользователем.** Клиенты могут работать в любой локальной зоне, но передают серверу расписание уже в **UTC**. Сервер хранит дни недели и интервалы в UTC и вычисляет открытость по UTC; не выводит зону из города или системного времени сервера. Пятница 22:00–02:00 UTC открыта в субботу 01:00 UTC. Входящий локальный интервал должен быть переведён в UTC до отправки; `DateTime` без UTC kind на доменной границе отклоняется. Если впоследствии продукту понадобится хранить местное расписание заведения, это будет отдельное изменение контракта с zone ID, правилами DST и миграцией старых интервалов; трактовать уже сохранённые UTC значения как местные нельзя. Зависимые задачи: P23, P24, P34.

## ADR-03. Цена и наличие меню — решение обновлено 19 октября 2026

Пользователь отменил объём напитка как поле меню. Он удалён из ручного API, публичного ответа, снимков, OCR, discovery-фильтров и `ShopMenuItems`. Старые JSON-запросы ручного меню и сообщения с дополнительным `volumeMl` читаются без использования этого поля.

`Present` требует `price > 0`; `Absent` и `Unknown` требуют `price = null`. Неизвестный enum, пустой/неизвестный slug, дубль напитка и цена больше `numeric(10,2)` отклоняют весь ручной пакет с 400 до записи. Moderation и Shops используют общую проверку значений. OCR-строка без положительной цены пропускается целиком; из дублей сохраняется минимальная цена. Ручные правки сохраняют приоритет над OCR.

Миграция `RemoveDrinkVolumeFromMenus` удаляет старый столбец и меняет CHECK. Исторические миграции остаются. Старые writers нужно остановить до миграции, затем запустить новые Shops и Moderation. Возврат старой версии требует резервной копии, поскольку удалённые объёмы восстановить из нового меню нельзя.

## ADR-04. Одна позиция на напиток — утверждено

**Сейчас.** В БД уникальна пара `(ShopMenuId, DrinkDefinitionId)`. Парсер при дубле берёт минимальную цену, оставляя объём первой строки: вход «300 мл за 12; 200 мл за 8» может стать «300 мл за 8». Источники: [MenuConfiguration](../CoffeePeek.Shops.Persistance/Configuration/ShopMenuConfiguration.cs), [ParseMenuPhotosHandler](../CoffeePeek.Shops.Application/Features/Menu/ParseMenuPhotos/ParseMenuPhotosHandler.cs).

**Утверждено пользователем.** Для каждого напитка в меню кофейни существует не более одной позиции; уникальная пара `(ShopMenuId, DrinkDefinitionId)` соответствует продуктовой модели. OCR-дубли одного напитка нельзя превращать в несколько порций или склеивать цену и объём из разных строк.

После удаления объёма 19 октября 2026 OCR-дубли разрешаются выбором минимальной положительной цены. Одна позиция на напиток и приоритет ручного изменения сохранены.

## ADR-05. Приоритет ручной правки и устаревший OCR

**Сейчас.** `MergeParsedItems` не переписывает позицию с `Source=Manual`, но `ApplyParseResultAsync` без версии вновь добавляет фотографии из старого снимка и завершает статус обработки. `ShopMenu` хранит статус и `CapturedAtUtc`, но не идентификатор задания и не ревизию состава фото. Источники: [ShopMenu](../CoffeePeek.Shops.Domain/Aggregates/MenuAggregate/ShopMenu.cs), [ApplyShopMenuService](../CoffeePeek.Shops.Application/Services/ApplyShopMenuService.cs).

**Утверждённое правило конфликта.** Любая ручная правка после запуска OCR делает этот job устаревшим: результат **отклоняется целиком**, включая найденные новые позиции, цену, suggested range, статус и фотографии. Пример: запущен A; пользователь вручную меняет цену одной позиции; приходит A с десятью позициями → ни одна из десяти не применяется. Ответ A не меняет состояние более нового job B.

**Предлагаемый механизм.** Каждому OCR-заданию назначить `JobId`, исходную ревизию меню и fingerprint набора photo IDs/keys. Изменение или удаление фото также инвалидирует job и не восстанавливается поздним ответом. Повтор уже применённого job возвращает его зафиксированный исход. Пример: запущен A для фото X, X удалено, приходит A → меню и фото не меняются, статус A=`Stale`; новый B остаётся текущим. Формат fingerprint и хранение результата требуют P15/P27.

**Совместимость.** Старые сообщения без revision нельзя объявить актуальными по умолчанию. P27 должен определить drain/legacy adapter/quarantine с журналом; внешнюю сериализацию менять после контрактных fixtures. Для устаревшего job добавление *других* новых позиций уже запрещено утверждённым правилом. Зависимые задачи: P15–P17, P27.

## ADR-06. Удаление справочников и ссылочная целостность

**Сейчас.** `DeleteCityHandler`, `DeleteEquipmentHandler`, `DeleteRoasterHandler` физически удаляют строки. `Location.CityId` кофейни индексирован, но FK на `Cities` не настроен; для некоторых других связей FK есть. `ShopTag` умеет деактивацию. Источники: [AdminCityHandlers](../CoffeePeek.Shops.Application/Features/Admin/Catalogs/Cities/DeleteCityHandler.cs), [AdminEquipmentHandlers](../CoffeePeek.Shops.Application/Features/Admin/Catalogs/Equipments/), [AdminRoasterHandlers](../CoffeePeek.Shops.Application/Features/Admin/Catalogs/Roasters/), [CoffeeShopConfiguration](../CoffeePeek.Shops.Persistance/Configuration/CoffeeShopConfiguration.cs), [AdminShopTagHandlers](../CoffeePeek.Shops.Application/Features/Admin/ShopTags/).

**Утверждено пользователем для городов.** Если `City C` используется кофейней, DELETE C возвращает `409 Conflict`; сведения о городе и `Location.CityId` остаются прежними. Проверка должна учитывать гонку параллельного создания ссылки, поэтому P09/P29 должны защитить правило FK/Restrict и проверить его на реальной БД. Для старых осиротевших значений нужен отчёт и ручная политика восстановления до constraint, без автоматической подмены города.

**Предложение для других справочников.** Удаление используемого оборудования/обжарщика/напитка также отклонять как `409`; сведения и назначения сохраняются. Неиспользуемую запись можно удалить только после проверки всех ссылок и DB Restrict. Если справочник поддерживает `IsActive`, деактивация исключает новые назначения, но не стирает исторические. Это расширение правила города на другие сущности **не утверждено**.

**Открытый продуктовый вопрос.** Должны ли неиспользуемые записи физически удаляться вообще или оставаться деактивированными? Отдельно решить видимость деактивированных тегов/оборудования в исторических карточках. Зависимые задачи: P09, P11, P19, P29.

## ADR-07. Основное оборудование отдельно для кофейни — утверждено

**Сейчас.** `Equipment.IsPrimary` лежит в общей сущности справочника. `CoffeeShop.AddEquipment` может вызвать `UnmarkAsPrimary()` на экземплярах оборудования. Связь — many-to-many `CoffeeShopEquipments`, без собственной модели назначения. Источники: [CoffeeShop](../CoffeePeek.Shops.Domain/Aggregates/CoffeeShopAggregate/CoffeeShop.cs), [CoffeeShopConfiguration](../CoffeePeek.Shops.Persistance/Configuration/CoffeeShopConfiguration.cs).

**Утверждено пользователем.** `IsPrimary` относится к назначению оборудования **в конкретной кофейне**, а не к общей модели `Equipment`. В каждой категории для каждой кофейни допустима **не более одной** primary-единицы; ноль допустим, если выбор ещё не сделан. Изменение выбора в кофейне A не меняет кофейню B. Целевая запись — отдельная связь `ShopEquipment(ShopId, EquipmentId, IsPrimary)` либо эквивалентная модель назначения с уникальностью по `(ShopId, CategoryId)` для primary; общий справочник не мутируется при смене primary. Текущий глобальный флаг не позволяет точно восстановить прежний выбор каждой кофейни: backfill должен выделить неоднозначные связи и не выдавать догадку за исторический факт. Зависимые задачи: P11, P29.

## ADR-08. Конкурентная правка, повтор и конфликты

**Сейчас.** Публичный адрес использует `ExpectedRevision` и `409`; `CheckIn` имеет `RowVersion`, `ContentRevision` и последовательность moderation decision. Для профиля/меню сопоставимого общего механизма нет. Источники: [PublicAddressService](../CoffeePeek.Shops.Persistance/PublicAddresses/PublicAddressService.cs), [CheckIn](../CoffeePeek.Shops.Domain/Aggregates/CheckInAggregate/CheckIn.cs), [ShopMenu](../CoffeePeek.Shops.Domain/Aggregates/MenuAggregate/ShopMenu.cs).

**Утверждено пользователем для профиля.** Admin и owner сверяют **одну ревизию всего профиля кофейни**, а не независимые ревизии отдельных разделов. Пример: оба читают v7, admin записывает v8, owner с v7 не перезаписывает данные admin и получает конфликт. К профилю относятся основные поля, контакты, место, расписание и связи со справочниками; одна атомарная profile-команда увеличивает ревизию один раз. В ответ admin/owner добавляется `ProfileRevision`; оба существующих PUT принимают необязательный `If-Match` и возвращают `409` при несоответствии, EF concurrency token закрывает гонку между чтением и записью. Старый PUT без заголовка продолжает работать: одновременные записи с одной исходной ревизией конфликтуют, но **последовательная запись со старым снимком может перезаписать предыдущую**. Это явное ограничение совместимого перехода; обязательный условный запрос вводится позже в отдельной версии API после миграции клиентов.

**Фактически защищённые writer paths после P10.** `UpdateAdminCoffeeShopHandler` и `UpdateOwnerCoffeeShopHandler` проверяют переданную ревизию до мутации, увеличивают её один раз и полагаются на EF concurrency token при commit; `SetAdminCoffeeShopFocusHandler` и `SetShopPrimaryEquipmentHandler` также увеличивают эту же ревизию. `If-Match` принимает неотрицательное десятичное число в кавычках или без них; `409` возвращается в прежнем `Response<T>` envelope. В PostgreSQL сценарий двух одновременно загруженных admin/owner копий проверяется gated тестом `ShopProfileRevisionLiveTests`; локально без PostgreSQL он пропускается.

**Состояние реализации и остаточный риск.** Оба profile PUT, focus, primary, visibility, gallery add/remove, tags, owner assignment, import enrichment и применение неменю-разделов Moderation увеличивают `ProfileRevision`; ветки Menus → Shops увеличивают её при изменении `PriceRange`. Проверка stale Moderation → owner добавлена в обязательный PostgreSQL gate, локально без БД пропускается. Профильный EF-конфликт преобразуется в неретрабельный `409` до общей Wolverine retry-политики. Защита всё ещё распределена по writer paths, а не сосредоточена в одном модульном порту; новые пути нужно включать в ревизию и проверять архитектурным тестом. Совместимый legacy PUT без `If-Match` остаётся уязвим к последовательной stale-записи.

**Предложения, ещё не утверждённые этим ответом:** точный формат значения `If-Match` и тела `409`, отдельная ревизия меню, idempotency key с правилом одинаковое тело → тот же результат / другое тело → конфликт, и политика повтора доставленных событий. Бесконечный автоматический retry пользовательского конфликта недопустим. Зависимые задачи: P06, P07, P10, P13, P15, P27.

## ADR-09. Атомарность пакетной команды и импорта

**Предложение.** Пакетная ручная команда меню целиком успешна или целиком отклонена до мутации. Неизвестный slug в списке `[valid, unknown]` возвращает 400 и не сохраняет `valid`; текущее тихое пропускание в [UpdateAdminShopMenuHandler](../CoffeePeek.Shops.Application/Features/Admin/Menu/) прекращается после принятия контракта. Ошибка позднего поля профиля не сохраняет ранние поля; это уже исправлено для admin/owner, но требует PG/Wolverine проверки. Ответ об ошибке не является успешным commit.

Импорт кофе — отдельный явный контракт: сейчас `ImportAsync` применяет снимок в транзакции и хранит `CoffeeImportRun` со статусом, snapshot identity и полнотой; запись failure делается отдельно. Не смешивать «весь HTTP-пакет атомарен» и «допускается частичная обработка импорта». Предложение для P21 — единица атомарности один проверенный снимок источника; частичное применение возможно только после отдельного контракта с checkpoint и статусом. Повтор `(SourceKey, SnapshotId, PayloadHash)` возвращает прежний результат, тот же ID с другим hash — конфликт. Источник: [CoffeeCatalogStore.Import](../CoffeePeek.Shops.Persistance/CoffeeCatalog/CoffeeCatalogStore.Import.cs). Зависимые задачи: P06, P13, P21, P28.

## ADR-10. Публичная совместимость и состояния ответа

**Предложение.** Сохранять существующие маршруты и wire enum там, где это не противоречит утверждённым решениям. Для `isOpen` во всех API утверждено `null` при пустом расписании: текущий legacy `bool` должен стать nullable, совместимость клиентов и сериализацию проверить явно. Иные изменения смысла проводить через версионированное поле/API и fixture `old request → old response`, `new request → new response`. Если вход содержит неизвестный числовой enum, предложение — ошибка 400 с указанием поля. `null` как «не сообщено» и пустой массив как «явно нет записей» различать там, где это влияет на изменение. Скрытый объект не попадает в публичный read model; admin/owner правила доступа проверяются отдельно.

**Открытые решения продукта.** ADR-03 (верхние пределы, противоречивый `Absent/Unknown`), ADR-04 (выбор одного из валидных OCR-дублей), ADR-06 (delete или deactivate неиспользуемых записей и правила остальных справочников), ADR-08 (формат конфликта, ревизия меню и idempotency key). ADR-01, ADR-02, одна позиция на напиток в ADR-04, правило `Present`/OCR в ADR-03, правило устаревшего OCR в ADR-05, конфликт при удалении используемого города в ADR-06, primary отдельно для кофейни с максимумом один на категорию в ADR-07 и одна ревизия всего профиля в ADR-08 утверждены; их реализация и проверка API/очередей всё ещё обязательны. P34 проверяет принятые варианты на реальном HTTP и сериализации событий.

## ADR-11. Инварианты основного профиля — техническая защита, бизнес-переходы открыты

**Существующий контракт.** У `CoffeeShop.Name` есть ограничение БД на 100 символов, у `Description` — на 500; `Name` обязателен. Доменные и контрактные перечисления цены имеют только `Cheap`, `Moderate`, `Expensive`; у статуса — `Active`, `TemporarilyClosed`, `PermanentlyClosed`; у фокуса — `Specialty`, `CoffeeBar`, `Cafe`. `CoffeeFocusType?` допускает отсутствие значения. Поэтому конструктор и методы изменения профиля проверяют непустое имя, длины и известные числовые значения enum до изменения полей. Admin и owner проверяют основные поля до применения расписания, контактов и каталогов; ошибочный запрос возвращает 400 без мутации отслеживаемого агрегата. Это техническое закрепление уже существующих ограничений, а не новое продуктовое правило.

**Открыто для продукта.** Следует ли нормализовать ведущие/замыкающие пробелы имени и пустое описание, какие переходы `PermanentlyClosed → Active` допустимы и кто их вправе выполнять, а также означает ли `CoffeeFocusType=null` «неизвестно» или отдельное состояние. До решения сохраняем исходный текст непустого имени и описания, nullable фокус и все переходы между тремя уже существующими статусами. Не вводим автоматическую нормализацию либо запрет переходов задним числом. При утверждении иной политики потребуется проверить импорт и moderation event, где значения приходят из другого сервиса.

## Минимальный набор примеров для тестов

| Номер | Вход | Ожидаемый результат по предложению | Уровень |
| --- | --- | --- | --- |
| T01 | Active + `Schedules=[]`, запрос `isOpen=true/false` | Не проходит оба фильтра; карточка `null` | HTTP + PG, обе реализации поиска |
| T02 | UTC пятница 22:00–суббота 02:00, суббота 01:00 | Открыто | Domain + PG projection |
| T03 | `Present, price=-1`; `Present, volume=null`; OCR `(price=8, volume=null)` | Ручные строки отклонены; OCR-строка пропущена целиком; прежние данные неизменны | Domain + PG SQL/EF + OCR fixture |
| T04 | OCR `(12,300)` и `(8,200)` одного drink | Цельная пара `(8,200)` | Parser fixture |
| T05 | После запуска OCR A вручную изменена одна позиция, ответ A запоздал | Весь ответ A отклонён: нет новых позиций, цены, фото и suggested range; A stale | PG + очередь |
| T06 | Существующий city C удаляют при параллельной новой ссылке | Один согласованный `409`/FK отказ; orphan невозможен | Два PG подключения |
| T07 | Две кофейни используют один equipment; в A меняют primary | B не меняется | PG |
| T08 | Два редактора обновляют v7 | Один commit v8, другому 409; нет lost update | PG + HTTP |
| T09 | Пакет меню `[valid, unknown]` | 400 и ноль изменений | HTTP + Wolverine + PG |
| T10 | Повтор import key с иным hash | 409, старый импорт и данные прежние | PG |
| T11 | Ручной пакет содержит два ряда одного drink с разными ценами | 400; ни одна позиция пакета не записана, прежнее меню неизменно | HTTP + PG |
