# P27: исходная матрица совместимости ShopsService

Срез исходников: 8 октября 2026 года, `HEAD f0cacf555699f051dbda26f79fdad92043db02ba` плюс незакоммиченное ранее исправление атомарности профиля. Этот документ — **база для P27**, а не готовая миграция сообщений. Он фиксирует обнаруженные HTTP и CLR-контракты, точки публикации и приёма. Точные имена RabbitMQ-очередей, wire identity сообщений и байтовые схемы сериализованных envelopes не извлекались из работающего брокера; перед изменением их нужно получить из runtime и брокера в той же версии и конфигурации, что развёрнуты сейчас.

## Что уже определяет совместимость

- `CoffeePeek.Shared.Persistence/Extensions/WolverineModule.cs` настраивает RabbitMQ `AutoProvision().UseConventionalRouting(NamingSource.FromHandlerType)`. В комментарии прямо указано, что у каждого handler своя очередь: `ModerationShopApprovedEvent` принимают и Account, и Shops. Следовательно, **CLR-имя handler нужно считать частью маршрутизации**, пока не подтверждён снимок реально созданных очередей и алгоритм их именования. Namespace/type сообщения также считать частью wire identity; точный формат Wolverine message-type header здесь не подтверждён.
- Тот же модуль включает durable inbox/outbox, durable local queues, PostgreSQL persistence, EF transactions и `DurabilityMode.Solo`. Это описание конфигурации, не доказательство доставки конкретного сообщения при сбое. `Solo` соответствует текущему одному экземпляру сервиса; переход к нескольким репликам требует отдельной проверки.
- `CoffeePeek.ShopsService/InfrastructureExtensions.cs` сканирует Application и Infrastructure assembly; host assembly служит application assembly для codegen. Не все HTTP запросы идут через Wolverine: `DiscoveryFavoritesController`, `AdminPublicAddressesController`, `InternalCoffeeImportController.Failures` вызывают store/service напрямую.
- В не-Development режиме `TypeLoadMode.Static` и `AssertAllPreGeneratedTypesExist=true`. Реестр `CoffeePeek.ShopsService/Internal/Generated/WolverineHandlers/GeneratedHandlerRegistry.cs` перечисляет обнаруженные handler-типы. После изменения handler, сигнатуры, namespace или сообщения нужен штатный `dotnet run -- codegen write` из `CoffeePeek.ShopsService` и проверки `CoffeePeek.ShopsService.Tests/WolverinePreGeneratedHandlersTests.cs`. Generated-файлы руками не редактировать. Startup-тест ловит отсутствующие существующие типы, второй тест сопоставляет discovered messages с generated classes; оба **не проверяют реальную RabbitMQ-доставку**.
- В локальном коде не найдено явных `ToRabbitQueue`, `ListenToRabbitQueue`, настройки message aliases или кастомного Wolverine serializer для Shops. Это **не** позволяет восстановить буквальные имена очередей без runtime-снимка. Имя файла с hash (`ParseMenuRequestedEventHandler1007143525.cs` и подобные) — имя сгенерированного .NET класса, а не подтверждённое имя очереди.
- Admin `PUT /api/admin/shops/{id}` и owner `PUT /api/owner/coffee-shops/{id}` сохраняют прежнее тело запроса. Необязательный `If-Match` принимает ревизию профиля (например, `"7"` или `7`); `AdminPublishedShopDto` добавляет `ProfileRevision` в ответ. Для условного запроса stale revision и EF race возвращают `409` в прежнем `Response<T>` envelope. Без заголовка legacy PUT остаётся допустимым и не защищает от **последовательной** stale-записи; это переходный контракт до обязательного условия в отдельной версии API.
- Новый Moderation отклоняет создание/изменение menu change request без `ExpectedInputRevision`. Уже сохранённый или ожидающий в очереди `ShopChangeRequestApprovedV1` с `ExpectedInputRevision=null` новый Shops consumer не применяет: он возвращает `ShopChangeRequestApplyFailedV1` с причиной для ручной сверки. Это осознанная несовместимость старого непроверенного snapshot с защитой ручной правки; такие события нужно найти и разобрать до cutover. DTO оставляет nullable поле ради десериализации старого сообщения.

Их надо версионировать/проверять отдельно от внешнего API.

`docs/api/examples` и `CoffeePeek.ShopsService.Tests/ApiExamplesContractTests.cs` содержат контрольные JSON примеры для публичного каталога напитков, check-in/feed; `CoffeePeek.ShopsService.Tests/{PublicAddressApiContractTests,DiscoveryHttpContractTests,CheckInControllerTests}.cs` проверяют отдельные HTTP-контракты. `ShopsCompatibilityContractTests` закрепляет ключевые controller route+verb, владельца путей в Gateway JSON, адресную форму публичного DTO, CLR identity нескольких межсервисных событий и handler-классов conventional routing. Это статический contract test, а не HTTP тест через работающий Gateway. Текущий OpenAPI route известен, но согласно `AGENTS.md` генерация `/openapi/v1.json` имеет отдельный pre-existing 500; не принимать пустой Scalar UI за отсутствие endpoints.

## Матрица перехода старый/новый

| Ситуация | Нужное состояние совместимости | Доказательство перед включением |
| --- | --- | --- |
| Старый publisher → старый consumer | Существующие URL, очереди, сообщения и generated registry работают до первого переключения | Снимок runtime endpoint/queue topology, брокерных `ready/unacked`, message-type headers, JSON fixtures, версия бинарников всех сервисов. |
| Старый publisher → новый consumer | Новый consumer умеет безопасно прочесть старое сообщение и применить старые правила, включая отсутствие новых обязательных полей | Serialization + RabbitMQ delivery test на **реальном старом envelope**, PG проверка идемпотентности. Для OCR V1 без revision — явная политика `ignore/quarantine/manual reconcile`, выбор после P15, а не автоприменение к новой версии. |
| Новый publisher → старый consumer | Пока хоть один старый consumer может получать сообщения, publisher не посылает несовместимый тип или обязательные новые поля по старому адресу | Canary с прежним бинарником; если совместимости нет — сначала обновить всех readers и только потом включить V2 publication. |
| Новый publisher → новый consumer | Новая версия имеет отдельную схему, idempotency key и проверенный route; старый тип остаётся обрабатываемым до завершения очереди | Generated registry, end-to-end RabbitMQ/PG тест, повторная доставка, offline/restart, наблюдаемость dead-letter/error queue. |
| Перенос handler в новый namespace/class | Старое имя очереди сохранено явной конфигурацией либо старые очереди осушены контролируемо | Сравнение точных очередей до/после, глубины очередей и bindings; deployment rollback. Просто смена namespace/class и успешный build недостаточны. |

Практический порядок P27 после P03/P07/P15: (1) снять топологию и сериализованные fixtures на развёрнутой версии; (2) зафиксировать полный старый `namespace.type`, handler CLR type, queue, exchange, binding и owner сервиса в отдельной machine-readable таблице; (3) добавить readers старой и новой схемы, regenerate codegen во всех затронутых сервисах; (4) выкатить readers, затем постепенно включить новые publishers; (5) измерять старые `ready/unacked`/error queues и число применённых/отклонённых сообщений; (6) после подтверждённого draining убрать старый маршрут и тип отдельным релизом. Перестановка очередей, renaming типов и изменение бизнес-правил не должны сливаться в один непроверяемый шаг.

## Неизвестное и обязательные проверки P27

1. **Точные RabbitMQ queue/exchange/binding names** для каждого handler неизвестны из статического исходника. `NamingSource.FromHandlerType` говорит источник имени, но не подтверждает буквальную строку в конкретной версии Wolverine, наличие префиксов, виртуального хоста и старых очередей после прошлых релизов.
2. **Сериализация Wolverine envelopes и message-type headers** не настроена явно в `WolverineModule.cs`; её фактическую форму нужно снять с реального сообщения/воспроизвести pinned version, а не выводить из имени record. Для вложенных DTO нужны fixtures, включая enum как number/string, `null`, пустые коллекции и DateTime kind.
3. **Все внешние producers/consumers в развёрнутой системе** статическим поиском локального репозитория не доказаны: могут существовать старые бинарники, ретраи, dead letters, ручные операции и внешние клиенты HTTP. Перед cutover нужен инвентарь окружения и очередь pending envelopes.
4. **Текущий generated code** доказывает наличие adapters в репозитории, но не гарантирует совпадение с работающим релизом. `WolverinePreGeneratedHandlersTests` не заменяет проверку брокера и дешифровку старого envelope.
5. **Gateway precedence и доступность каждого маршрута** по одной таблице маршрутов не полностью доказаны. Особый риск — общий `/api/admin/{**remainder}` у Account и специализированные Shops routes; нужны HTTP contract tests через Gateway для всех новых/перемещённых URL.

Работу P27 можно считать завершённой только после заполнения неизвестных runtime-снимком, фиксации JSON fixtures, реализации двустороннего перехода и тестов реальной доставки. Этот документ служит входом для такого изменения и не утверждает, что очередь уже осушена или новая версия сообщений выпущена.
