<objective>
Fix Sentry CP-SHOPS-SERVICE-34: `ParseMenuRequestedEventHandler.Handle` throws `ConflictException`
(wrapping `DbUpdateConcurrencyException`, "expected to affect 1 row(s) but actually affected 0
row(s)") from `unitOfWork.SaveChangesAsync(ct)` when two invocations race for the same `shopId`.

Root cause: `ApplyShopMenuService.GetOrCreateAsync` loads a tracked `ShopMenu` (with `Items`/`Photos`
children) via `ShopMenuRepository.GetTrackedByShopIdAsync`. `ShopMenu.ApplyParsedItems` /
`ReplacePhotos` do `_items.Clear(); _items.AddRange(items);` (same for `_photos`) on that tracked
graph. When two concurrent invocations (each its own DbContext) load the same row before either
commits, the first to `SaveChangesAsync` deletes/replaces the child rows; the second invocation's
`SaveChangesAsync` then issues a DELETE against child rows that no longer exist, and EF surfaces
that as `DbUpdateConcurrencyException`, which `UnitOfWork.SaveChangesAsync` wraps as
`ConflictException`. Wolverine already retries the *whole handler* on this exception
(`WolverineModule.cs`, `OnException<ConflictException>(...).RetryWithCooldown(50ms, 150ms, 400ms)`),
but the handler's Gemini vision parse call (`ParseMenuPhotosHandler.Handle`) takes ~30s, so a
concurrent second invocation is almost always still in flight when the outer retry fires — burning
a second expensive LLM call and reproducing the same race.

Fix: add a small bounded local retry (≤3 attempts) around *only* the apply+save step (not the
parse), clearing `IUnitOfWork`'s change tracker between attempts so the retry reloads the current
committed `ShopMenu` graph instead of operating on stale tracked entities. The outer Wolverine
policy stays in place unchanged as a last-resort safety net for anything the local retry can't
resolve in 3 attempts.

Purpose: stop concurrent/duplicate menu-parse events from repeating a ~30s paid Gemini call on every
conflict retry, and resolve the underlying save race without losing parsed menu data.

Output: `ParseMenuRequestedEventHandler` resolves the race locally in the common case; a new
`CoffeePeek.Shops.Infrastructure.Tests` project with regression tests proves the retry works and is
bounded.
</objective>

    where TDbContext : DbContext

    public async Task<int> SaveChangesAsync(CancellationToken ct = default)

        try

        }
        catch (DbUpdateException ex)
        {
            throw new ConflictException("A database conflict occurred. The record may already exist.", ex);
        }
