# Сбор каталогов кофе

Единая джоба читает 15 сайтов, включая Roast.by, Spiritus и публичную розничную витрину River Roasters на espressoclub.by. У сайтов разные форматы; сборщики используют общий JSON-контракт, HTTP-кеш и экспорт. Команда выполняет один полный проход и завершается:

```powershell
python -X utf8 dev/coffee-import/import_coffees.py
```

Этот запуск **всегда обновляет ответы из сети**. `--source spiritus.by --source espressoclub.by` выбирает отдельные источники; `--offline` повторно разбирает сохранённые ответы. `--output` задаёт общий каталог результатов; внутри создаётся отдельная папка каждого сайта с `coffees.json`, `coffees.csv`, `coffees.md` и `.cache`. `last-run.json` содержит отдельный статус каждого источника. Если хотя бы один источник не собран, код завершения — 1; остальные продолжают обновляться. JSON заменяется атомарно только после полного успешного сбора и записи таблиц. CSV/Markdown — файлы для просмотра, потребитель импорта должен читать JSON. HTTP-кеш не включается в Git; `--offline` требует ранее захваченных ответов на этой машине.

Подробная проверка новых сайтов, границы полноты и выводы для модели: [docs/coffee-parser-sources.md](../../docs/coffee-parser-sources.md). Российские сайты сохраняют RUB, остальные BYN; конвертации нет. Варианты могут различаться назначением обжарки при одинаковом весе. У Single Step и Tasty Coffee ключи вариантов составлены из родительского ID и опции: `identityKind == "option_combination"` отличает их от нативного SKU.

У семи новых адаптеров часть описательных характеристик пока помечена `detail_properties_not_collected`. У трёх одиночных товаров Daloni вес отсутствует в прочитанных данных: `weightGrams == null`, есть замечание для проверки. У Сварщицы и Tasty Coffee доступность сообщается на уровне карточки; это отмечено отдельно и не является подтверждением остатка каждого SKU.

Spiritus загружает витрину из публичного API Tilda. ID раздела извлекается из страницы, проверяется корневой каталог, все страницы сверяются с `total`; UID карточки и UID варианта сохраняются. В экспорт входят варианты с `Тип == "Зерно"`; молотые варианты не становятся весовыми SKU зерна. Пустое `quantity` означает отключённый учёт остатка и возможность заказа; `0` означает недоступный вариант. Одинаковые названия под фильтр и эспрессо имеют разные UID и остаются разными карточками.

River Roasters использует публичный JSON, ссылка на который указана непосредственно на `/storefront`. Это **зерно в наличии в кофейне**, не обещание онлайн-доставки: `availabilityScope == "in_store"`. Доступность определяется по `count > 0`; сохранено исходное время обновления витрины. Оптовый прайс `/b2b` не смешивается с розничными ценами. В JSON нет ID или отдельных URL товаров: ключ карточки — SHA-256 полного названия, ключ варианта включает граммы. `source_ids_not_provided` отмечает это ограничение. Переименование требует ручного сопоставления; названия разных обжарок не объединяются. Дубликат название/вес или неизвестный вес/остаток прерывает сбор.

Происхождение двух смесей Spiritus и двух карточек River не указано; страны остаются пустыми с замечанием. Страны из названия сохраняются с основанием и требуют проверки. Сборщики не угадывают состав и характеристики, отсутствующие на витрине.

## Ежедневная джоба на VPS

В `deploy/systemd/coffeepeek-coffee-import.service` и `.timer` подготовлен запуск каждый день в **03:00 UTC**, с интервалом 24 часа между плановыми запусками. `Persistent=yes` догоняет пропущенный запуск после простоя сервера; дополнительный ручной запуск может произойти раньше. Один systemd service не запускает второй экземпляр, пока первый работает. Результаты лежат в `/var/lib/coffeepeek-coffee-import`, логи — в journal. Таймер нужно установить и включить на Linux-сервере; в этом рабочем окружении он не активирован.

Для текущего VPS с checkout в `/opt/coffeepeek` (при другом пути исправить service), из корня репозитория:

```bash
sudo apt-get install -y python3-venv
python3 -m venv dev/coffee-import/.venv
dev/coffee-import/.venv/bin/python -m pip install -r dev/coffee-import/requirements.txt
sudo install -m 0644 deploy/systemd/coffeepeek-coffee-import.service deploy/systemd/coffeepeek-coffee-import.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now coffeepeek-coffee-import.timer
sudo systemctl start coffeepeek-coffee-import.service
systemctl list-timers coffeepeek-coffee-import.timer
journalctl -u coffeepeek-coffee-import.service -n 100 --no-pager
```

Сервис использует динамического непривилегированного пользователя; checkout и venv должны быть доступны для чтения/запуска. Для ручного обновления на VPS использовать `systemctl start` этого же service, чтобы сохранить защиту от одновременных запусков.

Перед включением таймера выполнить настройку из [coffee-catalog-api.md](../../docs/coffee-catalog-api.md): миграция Shops, соответствия брендов существующим обжарщикам и общий служебный токен Shops/Media/джобы. Создать `/etc/coffeepeek/coffee-import.env` из [примера](coffee-import.env.example); ограничить чтение файла администратором (`0600`). Таймер выполняет `--push`, поэтому эти параметры обязательны.

## Сохранение в каталог и фотографии

Обычный запуск без `--push` сохраняет только файлы. `import_coffees.py --push` сначала скачивает изображения, загружает их в закрытый Media API, затем применяет снимок через закрытый Shops API. Python не имеет доступа к PostgreSQL или ключам MinIO. Неисправный источник/изображение сохраняет прежний каталог этого источника; обработка остальных продолжается.

`publish_coffees.py dev/imports/roast-by/coffees.json` повторно отправляет уже собранный снимок, сохраняя его исходное время. `--offline --push` запрещён: повторный разбор кеша не является свежим наблюдением. Нужны переменные `COFFEE_IMPORT_SHOPS_URL`, `COFFEE_IMPORT_MEDIA_URL`, `COFFEE_IMPORT_TOKEN`; адреса ведут напрямую к сервисам во внутренней сети.

Изображения скачиваются с проверенных доменов сайтов/CDN, с интервалом не менее трёх секунд и лимитом 8 MiB. Поддерживаются JPEG, PNG, WebP, GIF, AVIF; SVG и HTML отклоняются. Media сохраняет исходные байты в бакете Shops под `coffees/<sha256>.<ext>` и помечает объект постоянным. Повторное содержимое использует тот же объект и метаданные. У Sorso, Sense и Marconi читается адрес ленивой загрузки `data-src`, у Blaser — слайдер карточки. River не предоставляет фотографий в публичном JSON: `photos=[]`, в админке `photos_not_provided`.

`.images/` хранит файлы и ETag/Last-Modified для условных запросов. `history/<source>/<snapshotId>.json` хранит запросы применения 30 дней; это идентификатор для сопоставления с `CoffeeImportRuns`. Оба каталога исключены из Git. Архивирование кофе не удаляет общий файл автоматически: один объект может использоваться несколькими карточками. Очистку неиспользуемых постоянных объектов добавлять при необходимости по ссылкам из обеих БД.

## Отдельный запуск Roast.by

`roast_by.py` собирает текущие разделы свежеобжаренного и зелёного кофе, проходит пагинацию и проверяет каждую карточку. Старые URL из sitemap не считаются товарами в продаже. Все запросы читают публичные страницы; корзина, аккаунт и оформление заказов не используются.

Из корня репозитория:

```powershell
python -X utf8 dev/coffee-import/roast_by.py --refresh
```

Нужны Python 3.10+ и Beautiful Soup (`requirements.txt`). Зависимость уже присутствовала в окружении, использованном для первого сбора. Для другого окружения:

```powershell
python -m pip install -r dev/coffee-import/requirements.txt
```

Результат по умолчанию сохраняется в `dev/imports/roast-by`:

- `coffees.json` — структурированный снимок, карточки и варианты упаковки, происхождение с кодами стран, исходные характеристики, ссылки на изображения, замечания для проверки и данные о полноте сбора.
- `coffees.csv` — таблица для просмотра; UTF-8 с BOM для Excel.
- `coffees.md` — таблицы с отдельными разделами для обжаренного зерна, зелёного зерна и кофе, доступного только молотым.
- `.cache` — исходные HTML и метаданные URL/времени получения/SHA-256. Кеш исключён из Git.

Повторный разбор сохранённых страниц без сети:

```powershell
python -X utf8 dev/coffee-import/roast_by.py --offline
```

Без `--refresh` используются уже сохранённые страницы, отсутствующие догружаются. Такой запуск удобен для продолжения прерванного сбора, но не является обновлением актуальных цен. `sourceSnapshots[].fetchedAtUtc` показывает время получения каждой страницы; `collectedAtUtc` — последнее время получения исходных данных. Для актуального снимка использовать `--refresh`.

Можно задать `--output` и `--cache`. Запросы последовательные, интервал не менее трёх секунд. При ошибке страницы, изменении групп вариантов или несовпадении числа найденных карточек со счётчиком категории сбор завершается с ненулевым кодом; ошибка сбора не заменяет существующие выгрузки неполным результатом.

## Формат и ограничения Roast.by

`products` содержит все доступные карточки из двух исходных категорий, включая отдельно помеченный товар только для помола. Для зерна фильтровать `productForm == "whole_beans"`; `productKind` отделяет `roasted_beans` от `green_beans`. Каждый размер упаковки — запись в `variants`, а не новая карточка. Возможные помолы хранятся в `grindOptions`: комбинации вес/помол не превращаются в выдуманные внешние SKU.

Цены передаются строками с двумя десятичными знаками и валютой `BYN`. Доступность вариантов берётся из `canBuy`; для товара без группы вариантов — из JSON-LD Offer. Возможность заказа не равна числу пачек на складе. Неактивные варианты сохраняются внутри доступного продукта со своим признаком; карточки, у которых нет доступных вариантов, попадают в `excluded`. Для таких карточек сохраняется `sourceProductId`, чтобы импорт обновил уже известные предложения.

`sourceProductId` — ID карточки, выбранной текущим каталогом. `externalVariantId` — ID конкретного предложения сайта. У Roast.by весовые карточки имеют собственные ID, связанные встроенной группой предложений. Импорт дополнительно сопоставляет продукт по уже известному ID варианта в группе: выбранная каталожная карточка может измениться. Название не является уникальным ключом; разные упаковки не объединяются только по совпадению названий.

JSON в HTML-атрибутах читается через JSON decoder, JavaScript сайта не выполняется. Источником характеристик служит JSON-LD. Если страна отсутствует в характеристиках, адаптер ищет явные утверждения о составе или название и отмечает результат в `reviewWarnings`. Образовательные абзацы о выращивании кофе не используются как полный состав смеси. Неоднозначное «Конго» не преобразуется автоматически в `CG`. Доли смеси остаются `null`, поскольку адаптер их не подтверждает.

`compositionKind` становится `blend`, когда это прямо следует из названия/характеристик. Для остальных товаров значение `unknown`: единственная страна не доказывает единый лот. `sourceProperties` сохраняет исходные характеристики, `evidenceField` — основание определения страны. Для смеси с неуказанными странами других компонентов есть отдельное замечание. Наличие замечаний не мешает сбору, но такие поля следует проверить до публикации в CoffeePeek.

Дрип-пакеты, капсулы, наборы из других категорий, чай и оборудование не входят в эту выгрузку зерна. Скрипт создаёт файлы и не пишет в базы CoffeePeek. Добавление `Country`, `CoffeeProduct`, DTO/API и публикации кандидатов описано в `docs/coffee-catalog-plan.md` и остаётся отдельной частью реализации каталога.

## Проверки

```powershell
python -X utf8 -m unittest discover -s dev/coffee-import -p 'test_*.py' -v
```

18 тестов проверяют варианты упаковки, цены, доступность, одиночный товар зелёного кофе, помол, смеси со списками состава, приоритет характеристик, неоднозначное происхождение, дубли внешних ID, границы пагинации и отказ от неполной выгрузки. Проверка новых платформ подтверждает разделение продавца/бренда, ценовые опции Tilda, Nuxt-данные и скидки Tasty Coffee, нормализацию ссылок пагинации и запрет POST к корзине. Проверка джобы подтверждает сохранность прежнего JSON при сбое одного источника. Все 15 источников повторно разбираются без сети из локального HTTP-кеша.
